### 发版清单（每版走一遍）

1. `app/build.gradle`：versionCode +1、versionName 按规则改
2. `Changelog.java` 顶部加 `Entry`，**code 必须等于 versionCode**（`ChangelogTest` 校验，对不上测试红）
3. 同步 `打工人闹钟-使用说明.md`（**头部版本号最容易漏**）与 `更新日志.md`
4. 跑 `tools/release.sh --check`：它一次性校验五处文档 + 全量测试 + lint，
   哪处没跟上会直接点名（不用等 Gradle 跑完 40 秒才发现）
5. `tools/release.sh` 出包：复制到 `/workspace`、算 MD5 与字节数、提示回填位置
6. 回填交接文档现状表的 MD5，更新 `布局现状清单.md`（若动了布局）
7. `git commit`

> **为什么有脚本**：一次发版要动五处文档、跑两轮 Gradle、复制 APK、算 MD5，
> 全靠人记就会漏。脚本把「能自动判的」全判了，只剩「需要写字」的留给人。

**灾备包不跟着每版走**（2026-10-26 用户明确）：只在**正式发布前**刷一次，
中间发版一律不动它。平时真正的备份是仓库自己的 `.git` 历史——它一直是最新的。
（`/workspace/打工人闹钟-灾备包-20261025.zip` 现有内容是 v0.80.1 那次刷的，
含 bundle + keystore + APK + 恢复步骤.md，做过真实恢复演练。下次刷新等上线前。）

## 4. 版本号规则（2026-10-26 重定：0.x 测试期 → 1.0.0 上线）

用户 2026-10-26 拍板：**测试期从 v0.x 起排，v1.0.0 留给正式上线那一天**。
理由是 v1.x 这个号段一旦用掉就回不去了，而测试期还会有删功能、改备份格式这类
破坏性改动——0.x 本来就允许这些（semver 惯例），1.0.0 才该是「承诺稳定」的时刻。

| 改动性质 | versionName |
| --- | --- |
| 加功能 / 改交互 / 删局部功能 / 界面重做 | **次版本 +1**，修订归零（0.80.0 → 0.81.0） |
| 修 bug / 调文案 / 调布局 / 纯文档 / 构建项 | **修订 +1**（0.80.1） |
| 正式上线 | **1.0.0**（之后按上两行继续） |

**判定口径**（有歧义时照这个判）：

- **改交互**：用户的点法变了——开关换成整行进对话框、弹窗从「按确定」改成「点即生效」。
- **调布局**：点法没变，只是位置、大小、颜色、字重、文案变了。
- **删局部功能**：删掉某个入口或某块 UI，主流程还在（删小组件上的请假按钮就属这档）。
- 只有「删掉一个主要能力」（比如整个请假体系、整个小组件）才够主版本——测试期不设主版本。

**versionCode 铁律**：每打一个包 +1，**永不复用、永不回退**。跳号允许且正确，空号不回收
（v0.56.0 撤掉年度闹钟那次跳过一个号，重排后跳号被抹平了，但规则不变）。

**versionName 与 versionCode 一一对应**：2026-10-26 重排后两条序列严格同步——
name `0.1.0 → 0.80.1`、code `1 → 182`，同一件事的两个写法。
`ChangelogTest` 校验最新一条 `Entry` 的 code 必须等于 `build.gradle` 的 `versionCode`。

**只有重排这一版需要卸载重装**：新包 code 182 < 旧包 188，覆盖安装会被系统拒绝
（签名相同也不行，系统只认单调递增）。卸载前先在 App 里「设置 → 导出配置」，装完再导入。
从 v0.81.0 起 code 又回到递增，以后正常覆盖安装即可。

**历史重排（2026-10-26）**：182 条从 v1.0 起按上面的规则重排成 v0.1.0 → v0.80.1，
旧号与新号的对照见 `docs/版本号重排-对照表.md`。
**仓库里已经没有 v1.x 了**——代码注释、布局注释、文档一次性扫干净（v1.41.0 → v0.54.1 这种），
`grep -r "v1\.[0-9]" app/src docs` 只剩 `v1.0.0`（未来上线版）和那张对照表的「旧号」列。
只有老截图、聊天记录里的 v1.x 需要查表。

**历史教训**：v0.56.1 / v0.56.2 / v0.56.3 三个版本全是首页布局调整，同一件事的
三次尝试却各占一个次版本号。**同一件事分几次做完，只涨修订号。**

**下一版**：按上表判断，**不再预先写死版本号**——待办表里只写「按规则递增」。

## 6. 待办

### 发布前总排期（2026-10-25 二次重排：商店暂缓，GitHub 开源优先）

用户 2026-10-25 拍板「按建议来」：**放弃现阶段上应用商店，改走 GitHub 开源 + 直接分发**。
理由：资质链（软著 + ICP + APP 备案 ≈ 1.5–2 个月 + 持续提审）是纯前置成本，而目标用户
（大小周 / 单休）聚集在社区而非商店搜索；源码白盒信任比商店 logo 更能说服「敢不敢装野包」。
**商店改为触发式**：出现「issue 里有人问上架 / star 过几百 / 非技术用户不会装 APK」任一信号再启动，
届时先上酷安（个人实名、无资质要求），全资质商店（小米 / 华为）最后。

排序原则：

1. **测试反馈 > 一切**。用户 2026-10-25 起真机测试 v0.74.2，先修反馈再加功能——
   否则新功能会掩盖旧问题，也给不出「这个 bug 是哪一版引入的」。
2. **A11 必须在假期倒计时和 A12 之前**。视觉不定稿，新功能和引导页都要二次返工。
3. **A12 必须最后**（老规则不变）：它描述 App 最终长什么样。
4. **发布项单独占最后一版（2.0.0）**，且不含新功能——代码冻结后再动构建项，
   出了问题能确定是构建项而不是某一版功能。
5. **小米超级岛只提报、不开发**：公开文档可核实的门槛是「在架应用」+ 场景方案两轮审核
   （运营 / 促销 / 借款类场景明确会被驳；闹钟类能否过预审无公开定论，以提报结果为准），
   不占关键路径。
6. **公开时机 = 测试反馈修完之后**（原定 P1 结束，因 P1 被审查修复占用而顺延）：
   不带已知 bug 公开；代码质量（574 测试、lint 0 errors、文档完备）已经是开源的好底子。

   场景：`startForegroundService` 在 `AlarmReceiver` 里就被系统拒（服务从未启动）→ 兜底通知
   `setOngoing(true)` 发出 → 服务侧的 `onDestroy` 取消逻辑不会执行 → 通知永远挂着。
   已 traced 两条消除路径：点通知里的「停止」按钮会经 `PendingIntent.getService` 把服务拉起来
   再 `stopSelf`，`onDestroy` 顺带取消，**这条通**；但**点通知本体**进 `AlarmActivity` 再按停止，
   `stopAlarm()` 不取消通知，**这条不通**。
   修法：`stopAlarm()` / `snoozeAlarm()` 里补 `NotificationManagerCompat.cancel(NOTIF_ID)`
   （对正常响铃流程无副作用——那时通知归前台服务管，`onDestroy` 反正也会取消）。
   已知小限制：两个闹钟同一分钟都走兜底时，第二条会顶掉第一条（共用 NOTIF_ID）——降级场景，可接受。
2. ~~**引导完成的后台重排有进程死亡窗口**~~ **v0.74.3 已修**。
   原来同步重排，v0.74.2 改成 `Reschedule.run(this, null)` 后立刻 `finish()`。Executor 通常
   毫秒级就跑完，但 MIUI 激进杀进程时，「引导刚设完 → 进程被杀 → 闹钟一条都没排上」是可能的，
   而用户下次打开 App 前不会知道。
   修法：**这条路径改回同步**。它是用户一次性点击，阻塞几百毫秒无感；ANR 风险来自反复操作，
   不来自一次性完成。其余界面侧路径保持后台。

## 8. 别再犯的坑

| 坑 | 教训 |
| --- | --- |
| 通知渠道改名只改字符串 | 名字建好就刻进系统库，**改代码无效**，只能换 ID 重建。`ChannelTest` 用 id→名字快照守门 |
| 拍脑袋估高度 | 「标题并卡」曾估省 188dp，实际每张卡要加 36dp 卡头，四张净省仅 44dp。**要算卡头，别只算内容** |
| 删了布局 id 还在测试里引用 `R.id.xxx` | 编译直接失败。改用 `getResources().getIdentifier(name, "id", pkg)` 断言返回 0 |
| 测试「隔离全绿、全套随机红」 | 八成是**静态状态被后台线程换掉**或跨测试串味。v0.76.0 实录：`App.onCreate` 的节假日自动检查真的连网，落地时 `REMOTE.clear()` 冲掉别的测试注入的数据（已加 `!BuildConfig.DEBUG` 门根治）。排查手法：在可疑点前后打印可识别的探针值，跑全套对比 |
| 想用 `ShadowSystemClock.advanceBy` 钉日期 | **没用**——Robolectric 不 shadow `System.currentTimeMillis()`，`LocalDate.now()` 读真实时间。日期相关测试只能「相对今天」构造数据；要固定语义就用固定日期的纯函数用例 |
| 反射测试跟着界面迁移失效 | `showWeekBigDialog` 等从 `MainActivity` 搬到 `SettingsActivity`，反射目标要一起改 |
| 使用说明头部版本号漏改 | 改了三处日志忘了头部。**发版清单第 5 步专门点名** |
| 一个功能分三刀做 | 占掉三个版本号，看起来像三次功能升级。**动手前想清楚整件事的样子** |
| 文档重复记录同一信息 | 现状表写 v0.54.2、实际 1.46.4。**同一事实只在一处写**。v0.56.5 起文档已进 `docs/` 随仓库版本控制，改错能 `git diff` 看出来——但写错仍然没人替你发现 |
| 窗口坐标先确认原点 | 去掉 `FLAG_LAYOUT_IN_SCREEN` 后 overlay 原点已在状态栏下方，再写 `y=状态栏高度` 就是偏移两次（v0.55.3 横幅下移 46dp 即此） |
| 权限之间的关系不能靠猜 | 「后台弹出界面」开了会连带开全屏通知（反之不成立）；电池优化对 `setAlarmClock` 无效，整行已删。**联动只能真机试；对结果没影响的开关，别放进检查清单** |
| 新 Activity 忘了注册 | v0.60.0 的二级页写好了却没写进 `AndroidManifest`，点进去 `ActivityNotFoundException` 闪退。**Robolectric 的 `startActivity` 不检查 manifest，全绿也发现不了**——补了一条 `PackageManager.resolveActivity` 断言。同类坑：新加广播接收器、服务同理 |
| 停止入口只靠权限 | 响铃页（后台拉起受限）、通知（权限可关）都可能没有，用户只能强行停止 App。**凡是「必须能停下来」的动作，要留一条不依赖权限的路径**——v0.58.0 的首页「正在响铃 · 停止」就是这条 |
| 界面外改状态不通知界面 | 通知栏按钮、桌面小组件改完 Prefs，界面不会自己刷新——刷新只在 `onResume`，而「退出去再进来」正好掩盖了它。Activity 之外改状态一律 `UiRefresh.request()` |
| 远程数据「空」不等于「没有」 | holiday-cn 提前建好明年的 `2027.json` 但 `days: []`，等国务院发通知才填。若把空数组当「该年无假期」合入，整年会被判成工作日——**比不更新更糟**。解析层必须把空数组当「未发布」跳过，`HolidayCnSourceTest.holidayCn_emptyYearNeverClearsExisting` 守这条 |
