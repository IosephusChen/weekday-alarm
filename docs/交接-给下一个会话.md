## 4. 版本号规则（2026-10-22 14:15 与用户确认）

用户原话：「1.47.0 以及更高版本号后续还可以用的，不用一直局限在 1.46.x 里」——
**1.47.0 可以重用**（当时那个包没发出去，不算占用），之后正常往上排。

| 改动性质 | versionName | versionCode |
| --- | --- | --- |
| 删功能 / 改数据格式 / 重写 | 主版本 +1，其余归零 | +1 |
| 加功能 / 改交互 | 次版本 +1，修订归零 | +1 |
| 修 bug / 调文案 / 调布局 | 修订 +1 | +1 |

**versionCode 铁律**：每打一个包 +1，**永不复用、永不回退**。跳号允许且正确
（115 是 1.47.0 撤掉留下的空号，不要回收）。同一个 versionName 可以对应两个 versionCode，
但必须是「同名不同号」的覆盖版——是补丁，不是常态。

**历史教训**：1.46.2 / 1.46.3 / 1.46.4 三个版本全是首页布局调整，同一件事的三次尝试，
却各占一个次版本号。**同一件事分几次做完，只涨修订号。**

**下一版**：修 bug 走 **1.46.5 / 120**；功能或交互改动走 **1.47.0 / 120**。

## 8. 别再犯的坑

| 坑 | 教训 |
| --- | --- |
| 通知渠道改名只改字符串 | 名字建好就刻进系统库，**改代码无效**，只能换 ID 重建。`ChannelTest` 用 id→名字快照守门 |
| 拍脑袋估高度 | 「标题并卡」曾估省 188dp，实际每张卡要加 36dp 卡头，四张净省仅 44dp。**要算卡头，别只算内容** |
| 删了布局 id 还在测试里引用 `R.id.xxx` | 编译直接失败。改用 `getResources().getIdentifier(name, "id", pkg)` 断言返回 0 |
| 反射测试跟着界面迁移失效 | `showWeekBigDialog` 等从 `MainActivity` 搬到 `SettingsActivity`，反射目标要一起改 |
| 使用说明头部版本号漏改 | 改了三处日志忘了头部。**发版清单第 5 步专门点名** |
| 一个功能分三刀做 | 占掉三个版本号，看起来像三次功能升级。**动手前想清楚整件事的样子** |
| 文档重复记录同一信息 | 现状表写 v1.42.0、实际 1.46.4。**同一事实只在一处写**。v1.46.6 起文档已进 `docs/` 随仓库版本控制，改错能 `git diff` 看出来——但写错仍然没人替你发现 |
| 窗口坐标先确认原点 | 去掉 `FLAG_LAYOUT_IN_SCREEN` 后 overlay 原点已在状态栏下方，再写 `y=状态栏高度` 就是偏移两次（v1.45.0 横幅下移 46dp 即此） |
