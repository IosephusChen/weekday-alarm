## 3. 阶段前提：现在是发布前，正确性优先

用户原话：「现在是我一个人在使用该 app，所有的设置项都丢了我也不在意，你只要按该做的去做就行，

**所以现在**：任何「为了不丢老用户设置而妥协」的做法都是错的，该改就改。

| 以前因为怕丢设置而没做的事 | 现在怎么做 |
| --- | --- |
| 通知渠道改名（名字建好就刻进系统，改代码无效） | 直接换 ID + 旧 ID 进 `App.CHANNELS_RETIRED`。v1.46.0 已照此办理 |
| Prefs 的 key 起得不好 / 语义变了 | 直接改 key，不写迁移代码 |
| 备份 JSON 字段名、结构要调 | 直接改，不兼容旧备份 |
| 数据文件格式要换 | 直接换 |

**等用户说「要发布了」，立刻切到兼容优先**，并在那一版之前做完（发布检查清单）：

1. **换签名**：现在用 debug keystore，发布必须换正式 keystore。换了之后已装设备无法覆盖安装，

2. **冻结渠道 ID**：`ChannelTest.EXPECTED` 当契约，之后改名要先算「值不值得让所有用户重设一遍」。
3. ~~**备份格式加 version 字段**~~ **已完成**：`ConfigBackup.FORMAT_VERSION = 1`，导出写 `format`、导入校验。发布前只需看提示文案够不够清楚
4. **Prefs key 冻结**：之后再改要写迁移。
5. 检查 `CHANNELS_RETIRED` 里的旧 ID 是否还在删。
6. **版本号收口**（用户 14:18 点名「发布的时候帮我好好弄一下」）：

## 4. 版本号规则（2026-10-22 14:15 与用户确认）

用户原话：「1.47.0 以及更高版本号后续还可以用的，不用一直局限在 1.46.x 里」——
**1.47.0 可以重用**（当时那个包没发出去，不算占用），之后正常往上排。

| 改动性质 | versionName | versionCode |
| --- | --- | --- |
| 删功能 / 改数据格式 / 重写 | 主版本 +1，其余归零 | +1 |
| 加功能 / 改交互 | 次版本 +1，修订归零 | +1 |
| 修 bug / 调文案 / 调布局 | 修订 +1 | +1 |

**versionCode 铁律**：每打一个包 +1，**永不复用、永不回退**。跳号允许且正确
（115 是 1.47.0 撤掉留下的空号，不要回收）。同一个 versionName 可以对应两个 versionCode，
但必须是「同名不同号」的覆盖版——是补丁，不是常态。

**历史教训**：1.46.2 / 1.46.3 / 1.46.4 三个版本全是首页布局调整，同一件事的三次尝试，
却各占一个次版本号。**同一件事分几次做完，只涨修订号。**

**下一版**：修 bug 走 **1.46.5 / 120**；功能或交互改动走 **1.47.0 / 120**。

**2. 二十四节气 —— 已完成（v1.51.2 引入，v1.53.0 改成公式算，v1.55.0 退出小部件格子）**

`SolarTerm.java` 用寿星通用公式 `[Y×0.2422 + C] − L`：C 是每节气每世纪的常数（20/21 世纪两张，各 24 个），
L 是闰年数。配 32 条例外修正（`FIX`），覆盖 **1900–2100**。已用 sxtwl 逐日比对 4824 个节气日期，全对。
两个坑：闰年的小寒/大寒/立春/雨水（1、2 月）公式会少一天，要补；剩下 32 个零星偏差靠例外表。
开关 `Prefs.isSolarTerms`，默认开；接入两处：`CalendarPanel`（App 日历）、
`MainActivity`（首页今日信息）。优先级 法定 > 农历 > 节气 > 基督教；补班日不覆盖。

> **v1.55.0 起不进小部件格子**：原来 `MonthWidgetRender` 里节气排在农历节日之后，
> 于是「霜降」会占掉那一格、把「班 / 休」顶掉——桌面日历上就看不出那天上不上班，
> 只能靠颜色猜。节气是知识性信息、一整天都不着急看，上班与否是决策性信息，
> 两者不该抢同一个位置。`WidgetRemoteViewsTest.monthCell_neverShowsSolarTerm` 钉住这条，
> 顺带断言开关开与关的计算结果一致（小部件格子根本不读这个开关）。
>
> **为什么不再用内置表**：v1.51.2 第一版内置 2020–2040 共 504 个日期，用户质疑「为什么内置、还覆盖那么多年」——
> 说得对，小部件只显示当月、21 年纯属多余，2040 年还得再发一版。会过期的表本身就是债。
> 用户还问过「能不能和节假日一起靠云端更新」：不建议。节气的数据源在数学里（天文事实、永远不变），
> 法定节假日的数据源在别人手里（国务院每年 11 月发通知、年年变）。给确定性的常量加网络依赖是净负担，
> 而且没网时还得靠内置表兜底——云端更新在这里替代不了任何东西。

**3. 农历节日 —— 已完成（v1.20 引入 8 个，v1.55.0 补到 12 个）**

`LunarCalendar.festival(d)` 逐条 if 判断，v1.55.0 补的四个：

| 节日 | 农历 | 说明 |
| --- | --- | --- |
| 龙抬头 | 二月初二 | 唯一的三个字，没有通用两字简称（「龙节」「龙头」都不成词），硬缩反而看不懂 |
| 中元 | 七月十五 | |
| 寒衣 | 十月初一 | |
| 小年 | 腊月廿三 / 廿四 | 北方廿三、南方廿四，App 不区分地区，两天都写「小年」 |

小年那两天不会被除夕规则截走：腊月最少廿九天，除夕最晚廿九，廿三/廿四永远不是除夕。
但**腊月可能横跨公历两年**——2027 年的腊月廿三是 2027-01-30，别在测试里写成 12 月。
`LunarCalendarTest.addedFestivals_2026And2027` 的日期全部由 sxtwl 反查，不是手推的。

**顺带说明另两套节日的数据来源**（用户问过，别再答错）：
农历 `LunarCalendar` 内置 1900–2100 的**历法**表（每年一个 int，201 个），因为朔望月没有闭式公式、必须查历书；
节日名只是 8 条 if（春节/元宵/端午/七夕/中秋/重阳/腊八/除夕）。基督教 `ChristianCalendar` 零数据表：
8 条固定日期 + 复活节现算（Meeus/Jones/Butcher），移动节日全由复活节推。两者都不需要「更新」，也不会过期。

  说关就关、没有备份。主源 jsDelivr（国内 30~40ms），备源 GitHub raw。
- **只拉今年 + 明年**，历史年份已内置。每次两个请求，不再拉一整份大文件。
- **远程层改成按年隔离**：`Map<Integer, YearData>`。原来是三个全局集合（全量替换），
  拉 2027 会把 2026 的远程修正冲掉。现在 `applyHolidayCnJson` 是增量语义，
  `applyRemoteJson`（旧格式）仍是全量替换，测试还在用。
- **空年份必须跳过**（这次最容易踩的坑，见第 8 节）：holiday-cn 会提前建好明年的文件但
  `days` 为空，等通知发布才填。解析层遇到空数组只置 `lastApplyOk = true` 并返回 false，
  **绝不动已有数据**——否则整年会被判成工作日，比不更新更糟。
- **缓存迁移**：旧的单文件自定义格式缓存（`holiday_remote_json`）换成年份键（`holiday_cn_2027`），
  用 `holiday_schema` 版本号做一次性清空，首次启动重拉。
- **远程层不带名字**：holiday-cn 的逐日 `name` 会连着九天都叫「春节」，不能直接用。
  未来年份的节日名靠农历层兜底（`CalendarPanel` 优先级 法定 → 农历 → 节气 → 基督教），
  所以 2027 春节仍显示「春节」，不会缺。

### v1.55.0 做了什么

## 8. 别再犯的坑

| 坑 | 教训 |
| --- | --- |
| 通知渠道改名只改字符串 | 名字建好就刻进系统库，**改代码无效**，只能换 ID 重建。`ChannelTest` 用 id→名字快照守门 |
| 拍脑袋估高度 | 「标题并卡」曾估省 188dp，实际每张卡要加 36dp 卡头，四张净省仅 44dp。**要算卡头，别只算内容** |
| 删了布局 id 还在测试里引用 `R.id.xxx` | 编译直接失败。改用 `getResources().getIdentifier(name, "id", pkg)` 断言返回 0 |
| 反射测试跟着界面迁移失效 | `showWeekBigDialog` 等从 `MainActivity` 搬到 `SettingsActivity`，反射目标要一起改 |
| 使用说明头部版本号漏改 | 改了三处日志忘了头部。**发版清单第 5 步专门点名** |
| 一个功能分三刀做 | 占掉三个版本号，看起来像三次功能升级。**动手前想清楚整件事的样子** |
| 文档重复记录同一信息 | 现状表写 v1.42.0、实际 1.46.4。**同一事实只在一处写**。v1.46.6 起文档已进 `docs/` 随仓库版本控制，改错能 `git diff` 看出来——但写错仍然没人替你发现 |
| 窗口坐标先确认原点 | 去掉 `FLAG_LAYOUT_IN_SCREEN` 后 overlay 原点已在状态栏下方，再写 `y=状态栏高度` 就是偏移两次（v1.45.0 横幅下移 46dp 即此） |
| 权限之间的关系不能靠猜 | 「后台弹出界面」开了会连带开全屏通知（反之不成立）；电池优化对 `setAlarmClock` 无效，整行已删。**联动只能真机试；对结果没影响的开关，别放进检查清单** |
| 新 Activity 忘了注册 | v1.49.0 的二级页写好了却没写进 `AndroidManifest`，点进去 `ActivityNotFoundException` 闪退。**Robolectric 的 `startActivity` 不检查 manifest，全绿也发现不了**——补了一条 `PackageManager.resolveActivity` 断言。同类坑：新加广播接收器、服务同理 |\n| 停止入口只靠权限 | 响铃页（后台拉起受限）、通知（权限可关）都可能没有，用户只能强行停止 App。**凡是「必须能停下来」的动作，要留一条不依赖权限的路径**——v1.47.1 的首页「正在响铃 · 停止」就是这条 |
| 界面外改状态不通知界面 | 通知栏按钮、桌面小组件改完 Prefs，界面不会自己刷新——刷新只在 `onResume`，而「退出去再进来」正好掩盖了它。Activity 之外改状态一律 `UiRefresh.request()` |
| 远程数据「空」不等于「没有」 | holiday-cn 提前建好明年的 `2027.json` 但 `days: []`，等国务院发通知才填。若把空数组当「该年无假期」合入，整年会被判成工作日——**比不更新更糟**。解析层必须把空数组当「未发布」跳过，`HolidayCnSourceTest.holidayCn_emptyYearNeverClearsExisting` 守这条 |
| 日志页一次性渲染全部条目 | 1.46.5 补录后 **114 条 ≈ 670 个 View**（旧记录估 570，低估了），进页面会卡。v1.46.6 已改分批（首帧 105），但**还没真机确认是否彻底不卡**——装上后留意一下 |
