## 二、还没动、但值得做的优化

按「用户感知 ÷ 改动成本」排序。

### ~~P1 · 主界面一屏放不下~~（v1.28.1 做、v1.34.0 部分回退）

现在主界面从上到下的高度大致是：

| 区块 | 高度 |
| --- | --- |
| 标题栏 | ~56dp |
| 今日状态卡（日期 + 28sp 状态 + 副标题 + 倒计时） | ~200dp |
| 「排班」卡（2–4 行） | ~110–160dp |
| 「闹钟」卡（2 条闹钟 + 添加按钮） | ~276dp |
| 「排班日历」卡（标题 + 表头 + 6 行 × 50dp + 图例 + 标记按钮） | ~460dp |
| 使用说明 + 测试响铃 + 运行状态 | ~150dp |
| **合计** | **≈ 1230–1280dp** |

360×640 的屏，内容高度约 560dp——要滚两屏多。日历卡一项就占了三分之一。

**建议**：把「排班日历」独立成页，标题栏加「日历 ›」入口（与「设置 ›」并列），主界面只留「今日状态 + 排班 + 闹钟」。
理由：日历是「核对与临时调整」用途，不是每天必看；而请假/加班两个入口跟着日历走，也顺理成章。
代价：请假入口深了一层——可让「今日状态卡」整块可点，直接进日历并定位到今天。

**后记（v1.34.0）**：这个判断错了一半。独立成页确实让首页变短了，但用户的真实反应是
「收起来还得手动点一下」——核对班表和临时标假是**高频**动作，不是「偶尔」。日历已搬回首页并默认展开，
换来约 1200dp 的主界面（滚两屏），同时把使用说明的 400dp 收成一行、去掉倒计时点击，净增可控。
**教训：判断「高频 / 低频」要按用户实际点击分布，不能按功能听起来像不像「设置」。**

### ~~P1 · 日历格子固定 46dp~~（v1.28.1 已做）

`renderCalendar()` 里 `cellHeight = 46 * density`，格子内是 13sp 数字 + 9.5sp 标签。
系统字体 1.5× 时内容约 42dp，刚好卡住；2.0× 时溢出，数字和标签会互相压。

**建议**：`cellHeight = max(46dp, 数字行高 + 标签行高 + 4dp)`，用 `Paint.FontMetrics` 算实际行高。
约 10 行代码，可加一条 Robolectric 断言（fontScale 2.0 时格子高度 > 46dp）。

### ~~P2 · 设置页「按键设置」摘要被截断~~（v1.29.0 已做）

`tvKeys` 的文案是「音量键：稍后提醒 · 电源键：关闭」，13sp 约 200dp；右侧还有 16sp 的 `›`，360dp 屏可用宽度约 280dp，余量很小。
字号再大一点就会被 `ellipsize=end` 截成「音量键：稍后提醒 · 电源…」。

**建议**：拆成两行副标题（`音量键  稍后提醒` / `电源键  关闭`），或把值缩短成「稍后提醒 / 关闭」。

### ~~P2 · 闹钟行缺少快捷操作~~（v1.29.0 已做）

改时间、改规则、删除，现在都要「点行 → 弹编辑框 → 改 → 保存」。删一条要四步。

**建议**：长按行弹「复制这个闹钟 / 删除」两项菜单。复制比删除更常用——「再来一条 8:00 的」。
成本主要在事件处理（现在行是动态生成的 `LinearLayout`，加 `setOnLongClickListener` 即可，不需要 RecyclerView）。

### ~~P2 · 小组件重复算一遍~~（v1.29.0 已做）

`MainActivity.refreshStatus()` 已经算过「下一个已登记闹钟」和「提醒总数」，紧接着 `Widgets.updateAll()` 里 `NextAlarmWidget.computeModel()` 又算一遍，其中 `nextRegisteredAlarm` 是逐候选 `PendingIntent` 探测（跨进程 IPC）。

**建议**：`Widgets.updateAll(ctx, NextAlarm next, int count)` 重载，主界面把算好的结果传进去；只有 `onUpdate` 自己算。
桌面没加小组件时本来就跳过（`getAppWidgetIds` 为空），所以收益只在「加了小组件」的用户身上——但那正是最在意这个 App 的人。

### P3 · 无障碍（感知弱，成本低）

- 日历格子是两个 `TextView` 竖排，TalkBack 会先读「21」再读「班」，中间没有停顿。
- 各行的 `SwitchCompat` 没有 `contentDescription`，TalkBack 只读「开关，已开启」，不知道是哪个闹钟。

**建议**：给格子设 `contentDescription = "10月21日 周三，上班"`；给开关设 `"起床闹钟开关"`。约 20 行。

### ~~P3 · 使用说明卡占地方~~（v1.34.0 已做）

主界面底部的「使用说明」有 9 条长文本，首次安装自动展开约 400dp。设置页已经有「重看新手引导」，功能重复。

**v1.34.0 做法**：收成一行「使用说明 ›」，点进去直接是引导页（`GuideActivity`）——那里一页一件事，
比一整屏小字好读，也没有新增页面。`guide_body` / `tv_guide` / `tv_guide_toggle` 一并删掉，
`Prefs.isGuideSeen` 至此只剩测试在用（保留是为了不牵动 8 个测试文件的初始化代码）。

## 三、新功能建议

按「对现有用户的价值 ÷ 实现成本」排序，前两条建议优先做。

### ~~1. 今天不上班（一键请假）~~（v1.28.1 已做）★★★★★

现在要标记今天请假：滚到日历 → 找到今天 → 点 → 确认。四步，而且日历在第二屏。

**做法**：今日状态卡右侧加一个小按钮「今天不上班」，点一下标记今天请假并重排；再点取消。
复用 `Prefs.addVacation` + `applySettingsIfEnabled`，几乎零新逻辑。
**成本**：半天。**风险**：无（误点可再点一次取消）。

### ~~2. 未来三次响铃~~（v1.29.0 做、v1.34.0 删）★★★★☆

倒计时只说「下一次」。用户常问的是「这周还有几次要早起」。

**做法**：点倒计时卡片，弹一个三行列表：`明天 07:30 起床` / `后天 07:30 起床` / `周四 12:30 午休`。
`ScheduleManager.nextRing` 已有，改成取前 3 个（加一个 `nextRings(..., limit)`）。
**成本**：半天。**风险**：无。

**后记（v1.34.0）**：上线一个月后用户评价「有点脱裤子放屁」——要多点一步才看到本来就能算出来的信息。
已连同 `ScheduleManager.nextRings`、`NextRingsTest`、倒计时的 `clickable/foreground` 一起删干净。
教训：**「能算出来」不等于「值得占一次点击」**，展示型功能先问「用户现在缺这条信息吗」。

### ~~3. 闹钟按用途着色~~（v1.30.0 已做）★★★☆☆

多闹钟时，「起床 / 午休 / 吃药」在列表里长得一样。

**做法**：编辑框加 4 个颜色圆点；列表时间大字用该颜色。
**成本**：1 天（要加字段、JSON、UI、迁移）。**风险**：低。

### ~~4. 小组件一键请假~~（v1.31.0 / v1.33.0 已做）★★★☆☆

睡前看到小组件写着「明天 07:30 起床」，想直接说「明天不上班」。

**做法**：`WeekScheduleWidget` 加一个「明天请假」按钮，发广播 → 改 Prefs → 刷新两个组件。
**成本**：1 天（RemoteViews 的按钮点击 + 广播接收器）。**风险**：中（RemoteViews 在不同 ROM 上的兼容性要真机验）。

v1.33.0 补上了同一行的「今天不上班」：早上洗漱时手机就架在旁边，那时的念头是「今天能不能不去」，
睡前和早上各有一个高频时刻，一个按钮只覆盖一半。两个按钮并排而不是分两行，是因为 4×2 的高度
经不起再加一行；语义跟着当天班别走（上班日=请假，休息日=加班），并排后「· 点此恢复」放不下，
改用实白底表示已生效。

### 4.5 闹钟总开关 ✗ 已删除，别再提（v1.46.4）

用户原话：「闹钟总开关似乎没有什么必要」。删了，连带 `Prefs.isEnabled` / `KEY_ENABLED` 一起清掉。

**别再以任何形式加回来**（包括「全部关闭」「一键静音」这类换名方案）：

- 每条闹钟行右侧本来就有独立开关，系统自带闹钟也没有全局总开关。
- 它制造静默失败：关掉后界面照常、就是不响，于是要在今日卡、倒计时、桌面小组件、
  睡前提醒、编辑弹窗五处补一句「总开关还关着」。一个功能需要五处解释自己，就不该存在。
- 它占第一屏最贵的 86dp，正好是日历月份行 + 星期头的高度。

真需要「长期不想响」：逐条关掉（打工人通常 1~3 条），或用日历上的「今天 / 明天不上班」。

### 4.6 日历默认折叠 ✗ 已否决（2026-10-22，没做，直接否）

打算把首页整月日历收成一行摘要「下一个休息日 · 10月25日 周日」，点开才是整月，
首页 1105 → 684dp，第一屏能余 16dp。线框、测算都做完了，**用户一句话否掉**：
「我觉得日历折叠这个功能没有必要」。

**否决理由（成立，别再捡）**：

- 折叠想解决的问题是「日历挤不进第一屏」，但 v1.46.4 之后首页顺序已经是「今天 → 闹钟 → 日历」，
  闹钟在第一屏，日历从第二屏开头开始——用户真正在意的「闹钟靠前」已经满足了。
- 核对班表、临时标请假是**高频**动作。折起来等于每天多一次点击，
  这正是 v1.34.0 把日历从独立页搬回首页时总结过的教训（「收起来还得手动点一下」）。
- 省下的 dp 是给「第一屏还能放点什么」用的，而现在第一屏已经没有待办要塞了。

**教训**：省空间是手段，不是目标。动手前先问「省下来给谁用」，答不上来就不该做。

### 5. 年度 / 节日闹钟 ✗ 已否决（试过，v1.47.0 做了又撤）

「每年中秋前一天提醒买月饼」「每年 3 月 1 日报税」。

**做过，v1.46.1 撤掉了。别再提。**

**否决理由**（不是「来不及做」，是「做了也不对」）：

- **需求错位**。生日、纪念日真正要的是「提前几天提醒买礼物」，不是「当天早上响一遍」——
  被叫醒时礼物已经来不及买了，而且人本来就要起床。响得准时，但没用。
- **它是这个 App 逻辑体系里的异物**。整套系统的心跳是「今天是不是上班日」，
  年度闹钟恰恰跟这一周无关，所以必须在四处被单独豁免：`ignoresVacation()`、
  `scanDays()`（90→367 天）、`nextRing()`（整体放宽）、备份字段 + 残缺数据分支。
  四处豁免就是四个 bug 温床，其中 `nextRing()` 那处还是全局的。
- **农历版更不值**。要补反向换算、闰月选择、除夕推算，2–3 天成本换「长辈农历生日」
  一个场景，而系统日历的农历提醒做得更好。

**如果将来真要做「每年某天提醒办事」**，方向不是更准的日期算法，而是「提前 N 天提醒」——
那需要的是一个倒数日/待办模块，属于另一个产品，别硬塞进 `Mode` 枚举。

### 6. 不建议做的

| 想法 | 为什么不建议 |
| --- | --- |
| 智能唤醒（浅睡期提前叫醒） | 需要长期采集心率/体动，要么加传感器权限，要么接手表 SDK。这个 App 的核心卖点是「不要权限也能准时响」，加进去就变味了。 |
| 响铃页显示天气 / 日程 | 要网络和日历权限，且刚被叫醒的人不会看天气。 |
| 云端同步配置 | 要账号体系。现在的「导出 / 导入 JSON」已经覆盖换机场景，成本却低一个数量级。 |

## 四、v1.32.0 补记：小组件从没加载成功过

「本周班表」组件从 v1.20 起就在布局里用 `<View>` 做今天的高亮层，而 `RemoteViews`
的允许列表里没有 `android.view.View`，启动器 inflate 时直接抛异常。数据模型全对，
所以所有基于 `computeModel()` 的单测都是绿的——这正好说明**只测数据不测视图会漏掉整类问题**。

已修，并补了 `WidgetRemoteViewsTest`（6 例）把两个组件的 `RemoteViews` 真正 apply 一遍。

## 四之二、v1.33.0 补记：小组件底部改成「今天 / 明天」并排

同一个组件、同一行位置，左边加了「今天不上班」。实现上有两处刻意绕开：

- **切换外观不换背景资源**。`RemoteViews` 里用反射式 `setInt(id, "setBackgroundResource", res)` 在部分启动器上会让整次更新失败、组件停在旧内容。改成同一格叠两层 `TextView`，只切 `setViewVisibility`。
- **旧广播 action 保留**。已经放在桌面上的旧组件实例，`PendingIntent` 里烧的还是 `TOGGLE_TOMORROW`；直接改名会让那批用户的按钮变成死键。新入口统一走 `ACTION_TOGGLE_DAY` + `EXTRA_DAY_OFFSET`，旧 action 转调 `toggleDay(ctx, 1)`。

最终 **358 个用例，0 失败**（v1.33.0 是 368；净减 10 条全部来自被删功能）。

**顺手清的债**：`MainActivity` 1473 → 1351 行（日历 567 行出去，换来面板初始化与双按钮几十行）；`CalendarPanel` 512 行。
离 900 行的目标还差，下一步该拆 `AlarmListRenderer`（列表渲染 ~160 行 + 颜色圆点 ~30 行）。

**两个坑值得记**：
1. `CalendarPanel` 的回调是 `applySettingsIfEnabled`，它会 `refreshAll()` → `calendarPanel.refresh()`。
   只要 `refresh()` 不回调，就不会递归；以后往面板里加「自动刷新」要守住这条。
2. 两个按钮并排后，「✓（点击恢复）」塞不下，文案收成「今天不上班 ✓」。
   **状态靠符号表达、不靠解释**——解释文字一多，等宽布局第一个崩。
   **后记（v1.34.1）**：这条对了一半。符号确实省地方，但 ✓ 在紫色渐变上太小，用户点完不确定生效没有；
   桌面小组件那边同样的动作会变成实白底 +「今天已请假」，两处观感还打了架。
   正解是**用底色承载状态、用文案说明结果**——「今天已请假」五个字和「今天不上班」一样长，
   一个字都没多占，白底一亮比任何符号都清楚。教训：省空间的正确姿势是换更短的**词**，
   不是把词砍成符号。

## 四之四、v1.35.0 补记：考勤记录 —— 一次「想做大的，最后做小了」的讨论

用户提「想做考勤记录」，第一轮说的是「工作日晚上加班了多久、工作日请假了多久、周末加班了多久，
还要月度统计」。我按字面算了一遍成本，结论是 5–7 天起步，而且最贵的那项做不出来。
第二轮用户自己澄清：**「就是大概看一下，让自己心里有个数而已，没有想得太复杂。」**

需求一变，答案完全不同——最后落地的是 1 天工作量，没有新页面、没有新数据模型。

### 砍掉的四项，以及为什么

| 想法 | 成本 | 砍掉的理由 |
| --- | --- | --- |
| 加班时长（几点到几点） | 5–7 天 | 闹钟 app 拿不到「几点下班」。要么加「标准下班时间」设置（不同公司不同、设错全盘错），要么让用户每天手填（三天就断）。断掉的记录比没有记录更危险——用户会以为那是真的 |
| 半天粒度（上午 / 下午） | 3–4 天 | 引入时段概念，还要改闹钟排程（上午请假 = 12:00 前的闹钟跳过）。而用户真正的痛点「同一天请假 + 加班」用双标记就解决了 |
| 月度统计页 | 1–2 天 | 用户原话「心里有个数」。日历本身就是月度视图，翻一翻就够了。加了数字反而要处理「同一天算一天还是两天」的口径 |
| 独立 app | 周级 | 数据全靠用户手标，拆出去两边必然不同步；且要正面竞争钉钉 / 飞书考勤，那三个有真实打卡数据 |

### 真正做的是什么

不是「加功能」，是**回退 v1.34.3 的一个判断 + 补一个入口漏洞**：

1. **回退**：v1.34.3 为了修「统计与清除对不上」，每次打开 App 就把过去的标记清掉。
   代价是日历翻回上个月一片空白——而「看看这个月哪几天请了假」正是日历最自然的用法。
2. **补漏**：渲染时 `vacation = inMonth && baseWork && ...`、`overtime = inMonth && !baseWork && ...`，
   按班休二选一。于是「工作日的加班」即使存了也不显示，入口也没有——用户想记「白天上班、晚上补工」时无处可点。

### 核心概念：按「今天」把标记切成两段

| 段 | 语义 | 可变 | 计入统计 | 批量清除 |
| --- | --- | --- | --- | --- |
| 今天及以后 | 排程开关 | 可增可删 | 计入 | 清 |
| 今天之前 | 记录 | 只读、可删 | 不计入 | 不清 |

这个切法一出来，v1.34.3 那个三方矛盾（格子印着假 / 统计不认 / 清除多清）自动消失：
「清除」只清还有排程意义的那段，数字与动作天然相等，不需要再靠「自动删数据」来对齐。

**教训**：v1.34.3 我用了「删数据」来消除不一致，那是最省事也最不可逆的一种。
正确做法是**把两个语义分开定义**，让它们各自自洽，而不是让一边迁就另一边。

### 另一个教训：需求要先问「用来干什么」，别急着估工时

用户第一轮列了三个粒度需求，我照着算了 5–7 天，还写了「先做最便宜的验证版」的策略。
第二轮他说「就是大概看一眼」，全部推翻。

如果一开始就问「你想拿这个做什么」，能省掉整整一轮推演。

### 后记（v1.35.1）：两段切法只活了一版

用户看完 v1.35.0 的下一句是：**「我需要过去的日子也能够标记。」**

理由比设计更硬：**请假常常是事后才想起来记的**——周三请了假，周五翻日历时才想补一笔。
把过去设成只读，恰好堵死了最自然的记录时机。而「只读」这个限制，是我从
「过去的标记不影响闹钟」推出来的，用户从来没提过。

改法很轻：菜单只留一套，过去与未来共用；`past` 只影响标题后缀（「· 已过去」）和
Toast 措辞（「已补记」而不是「当天闹钟跳过」）。数据层完全不动。

**连带必须改的是统计与清除**：既然过去也能标，标记就只是一条事实，没有「开关 / 记录」之分。
统计回到全部、清除也回到全部——否则又会出现「写 5 天、清完剩 3 天」，正是 v1.34.3 修掉的矛盾。

**教训**：语义分两段本身没错，错在**替用户决定哪一段该只读**。
「过去不影响闹钟」是技术事实，「过去不能标」是产品决定，两者之间隔着一次询问。

### 后记（v1.35.2）：统计与批量清除一起删了

用户接着问：「统计和清除按钮真的有必要吗？」——这次他的判断比我的设计更准。

- **统计**回答的是「历史上累计标了几天」。可他要的是「这个月哪几天」，日历格子就在眼前。
  而且这个数字只增不减，攒到几十天既不说明本月情况，也不说明任何要决策的事。
- **批量清除**是低频操作，却一次删掉不可恢复的全部历史。**误点的代价远高于省下的点击**。
  用户原话：「误标一定是会有的，但不会大量存在」——所以单日取消够用，批量清除是多余的能力。

**教训**：记录类功能里，**批量删除是负资产**，除非能撤销。加一个「清空」按钮很容易，
但它把「改一条」和「毁掉全部」放在同一个视觉层级上，用户迟早会点错。
真正需要的入口往往只有一个：**点那一条，改那一条**。
**用户描述的是他想象中的实现，不是他的目的**——这两者经常差一个数量级。

## 五、代码层面还留意到的

1. `Prefs.getAlarms()` 现在会「顺手关掉过期的一次性闹钟」并可能写盘。它被 10 多处调用，其中 `ScheduleManager` 的循环里每处都读一次。功能上没问题（幂等），但读路径带副作用这件事本身有隐患——将来若有人在 `onBind` 或渲染循环里调用，可能出现「读一次写一次」。已在本轮把首页三处合并成一次；其余路径建议后续逐步改成「显式 `refreshOnceAlarms()` + 纯读 `getAlarmsRaw()`」。
2. `MainActivity` 1351 行（v1.34.0 把日历拆成 `CalendarPanel` 后），仍承担「首页渲染 + 闹钟增删改 + 请假/加班按钮 + 权限引导 + 更新日志」。若继续加功能，建议先拆出 `AlarmListRenderer`（列表渲染 + 颜色圆点，约 190 行）。
3. `Alarm.java` 的 `onceDate` 用字符串存，`parseOnceDate()` 每次渲染都 parse 一次。列表 10 条时无所谓，属于「知道就好」。
4. 没有 `values-night` 的 `themes.xml` 里，`Theme.DaxiaoWeekAlarm.Ringing` 的 `windowBackground` 是紫色渐变——夜间也是同一份，这是对的（响铃页本来就该刺眼），不用改。
