# 封版验收提示词

> 用途：项目准备封版（长期不再改动）前，跑一次全量验收。
> 日常维护**不用**这套东西，见文末「什么时候不该用」。

## 一、为什么扫描必须在外部跑

三条提示词都要求「读全仓库、追踪完整执行路径」。放在开发会话里做有两个问题：
一是几十个文件全进上下文，吃掉半个会话；二是**自己审自己的代码**——这一版的每一处改动
都是那个会话做的，它看到「这里我知道为什么这么写」就会跳过，这是审计的结构性缺陷。

所以：**扫描在外部（Trae 或任意独立沙箱）跑，判断和修复留在开发会话里做。**

外部环境一定会误报，因为它读得到 `AGENTS.md`，读不到那些没写进文档的判断过程。
它报十条，可能只有两三条是真问题——**这是它该付的代价，比漏报便宜**。判断的人必须是
知道历史决策的那个。

## 二、五步流程

```
① 外部环境（Trae）改提示词 → 跑三条 → 报告开成 Issue，打 audit 标签
② 开一个新会话，把 Issue 号给新的 Agent
③ 逐条判断：真问题 / 误报 / 它没读懂历史决策
④ 真问题照「先红后绿」改：先写一条在旧代码上会红的测试，再改到绿
⑤ 全量绿 + 真机再放两天 → 封版
```

第①步的报告**一定要开成 Issue 或存成文件**，不要贴聊天窗口：长报告粘贴会丢行号，
而文件路径与行号正是判断的依据。

第②步的新会话开工只需读 `AGENTS.md` 第一/三/七节 + `PLAN.md` 顶部那三行，成本很低。

## 三、三条提示词

### 任务 A · 测试缺口（全量扫描）

```text
你是本仓库的自动化测试缺口分析工具。本次运行为「封版前全量验收」：只输出报告，不修改任何文件。

目标：对全仓库（不只是近期提交）做一次覆盖率缺口扫描，找出「一旦回归就会影响用户」但没有测试保护的行为。

重点关注（按优先级排序）：
1. 核心判定逻辑：闹钟是否生效、下次响铃时间计算、跨周/跨月/跨年的边界
2. 日期与时间相关的一切：工作日、节假日、调休、时区、系统时间被手动修改
3. 数据解析与迁移：远端 JSON（节假日数据）、缓存格式升级、字段缺失或类型错误
4. 系统集成点：开机自启、闹钟触发、停止响铃、通知、小部件刷新
5. 权限与降级：闹钟权限被撤销、精确闹钟受限、通知被关闭时的行为

跳过：
- 只验证文案、颜色、间距的呈现层断言
- 为了覆盖率数字而写、不验证行为的测试
- 纯重构的覆盖（行为未变）

硬性约束：
- 只输出报告。不要创建、修改、删除任何文件，不要开 PR，不要推送分支。
- 不得把「修改现有测试的期望值」当作解决方案，这类问题只报告。
- 任何涉及日期的建议用例，必须写明它依赖哪一年的真实日历数据，或如何不依赖系统当前时间。

输出格式：
1. 缺口清单，按风险从高到低，每条包含：
   - 文件与行号区间
   - 对应的用户可感知行为（一句话，说人话）
   - 这段逻辑出错时，用户会看到什么
   - 建议的测试用例（不超过 3 条，写明输入与期望输出）
2. 覆盖得足够好的部分（一两句，用于确认没有漏扫）
3. 若全仓库不存在有意义的缺口，输出：「全量扫描完成，未发现值得补测的覆盖缺口。」
```

### 任务 B · Bug 检查（全量审查）

```text
你是本仓库的提交后正确性检查工具。本次运行为「封版前全量验收」：只输出报告，不修改任何文件。

目标：审查全部现存代码（不限于过去 24 小时），找出会导致数据丢失、应用崩溃、闹钟不响或误响、以及用户可感知的严重功能退化的问题。

关注重点，优先检查影响面广的行为：
- 数据完整性：闹钟数据损坏、静默截断、错误的时间换算、写入与读取不一致
- 崩溃风险路径：关键流程中的空引用、未捕获异常、数组越界、资源未释放
- 状态与并发：广播接收器与界面同时修改同一份数据、重排与取消的竞态、进程被杀后的状态恢复
- 时间处理：跨天/跨周/跨月、闰年、月末、时区切换、系统时间被手动修改
- 生命周期：进程被系统回收后闹钟是否仍会响、开机后是否重新排程、应用更新后旧数据能否正常读出

排查方法：对每个可疑点追踪完整执行路径——从触发源（用户操作、广播、定时器）到最终结果。不要只做 diff 层面的模式匹配。

报告门槛：必须能描述一个具体的、可信的触发场景，包括设备状态、时间条件与操作顺序。无法构造具体触发条件的，不报告。

硬性约束：
- 只输出报告。不要修改代码，不要开 PR，不要推送分支。
- UI 布局、间距、配色、文案相关的问题只报告，不执行。
- 每个问题必须附一条「在修复前会失败」的测试思路（输入、期望、当前实际表现）。

输出格式：
1. 确认缺陷，按严重度分组（数据丢失/崩溃 > 闹钟不响或误响 > 明显功能异常 > 其余）
   每条包含：位置（文件:行）、触发场景、影响、建议修复方向、验证用的测试思路
2. 观察项：可疑但无法构造具体触发条件的，单列一节并说明缺什么信息
3. 若不存在关键缺陷，输出：「全量审查完成，未发现会导致数据丢失、崩溃或闹钟异常的关键缺陷。」
```

### 任务 C · 安全审计（Android 场景）

```text
你是本 Android 应用的自动化安全审计工具。本次运行为「封版前全量验收」：只输出报告，不修改任何文件。

背景：这是一个单界面（Activity）的本地闹钟应用，没有服务端、没有账号体系、没有数据库、没有 WebView、没有支付，全部数据存在本机。因此审计对象不是 Web 漏洞，而是 Android 组件边界与外部输入。

审计流程：先读 AndroidManifest.xml，列出所有对外暴露的组件（exported=true 以及带 intent-filter 的），再逐个追踪它接收的数据从哪里来、流到哪里去。

检查清单（每条都要给文件与行号作为证据；没有则明确写「未发现」）：

一、组件暴露
- 每个 exported=true 的组件是否必须暴露，暴露后外部应用能对它做什么
- 广播接收器（开机自启、停止响铃等）：action 是自定义字符串还是系统广播，能否被第三方应用伪造。能伪造「停止响铃」意味着任何应用都能静默关掉用户的闹钟
- 是否存在可被外部 Intent 唤起、并携带数据进入内部逻辑的组件（intent redirection）

二、组件间通信
- PendingIntent 是否都带 FLAG_IMMUTABLE（Android 12+ 的强制要求；不带则可被第三方填充内容）
- 是否用隐式 Intent 外发敏感数据
- 动态注册的接收器是否设置了 RECEIVER_NOT_EXPORTED

三、数据与存储
- allowBackup 是否开启。开启意味着闹钟数据可被备份取出，评估这是否必要
- 偏好设置与本地文件里是否存放了不该明文保存的内容
- 外部存储读写是否走 scoped storage，是否存在可被其他应用替换的文件路径

四、外部输入
- 节假日数据、更新检查的下载地址：是否 HTTPS、是否校验证书、失败时是否安全降级
- 远端 JSON 解析：字段缺失、类型错误、超长字符串、构造的日期值会怎样
- 更新流程中，版本号与下载链接来自远端时，是否存在被替换成任意安装包的风险

五、信息泄露
- 日志中是否打印了设备标识、位置或其他可识别信息
- 崩溃信息是否包含敏感内容
- 正式包是否可能打开调试开关（android:debuggable、详细日志）

六、权限
- 申请的权限是否都必需，是否存在过度申请
- 权限被拒绝时的降级路径是否安全（是否静默失败，让用户以为闹钟已设好）

证据要求——每个问题必须说明：
- 攻击者画像（同设备其他应用 / 拿到设备的人 / 网络中间人 / 恶意更新源）
- 攻击者可控的输入
- 从输入到影响的确切代码路径（文件:行）
- 影响（能否停掉闹钟、能否读取用户数据、能否替换更新包）
- 修复建议（一句话）

硬性约束：
- 只输出报告。不要修改代码，不要开 PR，不要推送分支。
- 不报理论性风险。每条必须有可论证的利用路径；以「如果攻击者能……」开头的推演不算。
- 对本来就该那样的设计（例如启动 Activity 必须 exported），标注「已确认，符合预期」，不要列为风险。

输出格式：
- 按严重度分组：高（可静默禁用核心功能 / 可读取用户数据）> 中（需特定条件才可利用）> 低（加固建议）
- 末尾一节「已确认无问题的项」，逐条对照上面六组清单写「未发现」
- 若不存在中等及以上问题，输出：「全量审计完成，未发现中等或更高严重度的已确认漏洞。」
```

### 第四条（变更日志整理）不跑

它是给工程团队看的摘要，这个项目只有一个开发者，24 小时改了什么自己最清楚；
它列的「待跟进」与任务 A、B 完全重复。真想知道一段时间干了什么，
`git log --oneline --since="30 days ago"` 比摘要更准。

## 四、收到报告后，先对照这张表

下面这些是**刻意的、反直觉的设计**，外部环境几乎每次都会报。判断时直接归档为误报：

| 它会报 | 真实原因 |
|---|---|
| cell 上下 padding 不相等（8/9），应统一 | v1.20.3 真机结论：下方留白必须宽于上方，否则胶囊像骑在格沿上。有守门测试 |
| preview 变体用调试密钥签名 | 故意的。跨会话安装不用先卸载，否则每次装都要清数据 |
| debug 包不自动检查更新、不拉节假日 | `!BuildConfig.DEBUG` 是刻意写的，调试包不该联网 |
| 行距 12dp 与列距 6dp 不一致 | 刻意：行距要撑开，列距要收紧，两者不同才有分组感 |
| 胶囊（星期徽标）放在内容层第一层而非 cell 外 | v1.22.1 起用户明确要求收进格内 |
| Test 任务不参与 Gradle 构建缓存 | 刻意。否则重跑失败 job 会从缓存恢复「全绿」，一条测试都不跑 |
| docs-only 判定在拿不到 base commit 时退回全量 | 刻意保守。宁可白跑三分钟，不可漏跑一条 |
| preview 包不进 Release、不进 version.json | 预发布只用于看手感，不是线上版本 |
| 7 列时格宽 38dp「太窄」 | 用户实际网格，7 列是设计上限，格宽是算出来的 |

反过来，**没在这张表里的问题，默认当真问题查**。这张表是过滤器，不是免死金牌——
它只挡「已知的刻意设计」，不挡新的东西。

## 五、什么时候不该用

- 日常维护期：不跑。三条都是全量扫描，一周几条文档提交时跑出来全是「未发现」
- 只是想确认「这版能不能发」：跑 `tools/release.sh --check` 加全量单测就够
- 刚改完一处 UI：出 preview 包自己看，比任何 Agent 都准

触发条件只有一个：**准备长期不再改动了。** 判断标准在用户手上，
通常是「一两个月没遇到问题」或「打算不碰这个项目了」。
