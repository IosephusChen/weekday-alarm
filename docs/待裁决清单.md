### A5 落地记录（2026-11-10 23:45，用户「A5 今晚做掉」）

**换掉了什么**：系统 Toast → 应用内提示条（`Hint`）。提示条是普通 `TextView`，加在
`android.R.id.content` 这个 `FrameLayout` 里，所以三件事自动成立——跟着 Activity 走（销毁就没了）、
键盘弹出时 content 被缩到键盘上沿、能主动 `cancel`。它不 clickable / focusable，
滑动手势照常落到下面的页面。

**5 个调用点各怎么处理**（对着上一节的表）：

| 段 | 界面 | 做法 |
| --- | --- | --- |
| v1 | 设置页「已是最新」 | `Hint.show`，底部 24dp |
| v2 | 关于页「已是最新版本」 | `Hint.show`，不再压底部版本 / MIT 小字 |
| v3 | 锁屏自测 | `Hint.show(..., 6000)`，`onPause` 里 `Hint.cancel`——计时还在跑，不收的话回页面会突然冒出来 |
| v4 | 「已发出，下拉通知栏看看」 | `Hint.show`，不再夹在说明与「上一步 / 开始使用」之间 |
| v5 | 「设置已更新 / 设置未改动」 | **不能在本页浮**：下一行就 `finish()`，提示条会跟着页面没。改成 `Hint.next()` 存给设置页，设置页 `onResume` 调 `Hint.showPending()` 浮出来 |

v5 这条是这次唯一新增的机制：`Hint.next` 存一个静态字段，目标页取走即清（同 `PendingTip`
的一次性语义，但不带 ok / warn 两句，因为它只服务这一处）。

**没换的 5 处**：`AlarmService`、`BedtimeReceiver`、`PreNoticeReceiver`、`SnoozeNotice`、
`FloatingAlarm`——Service / 广播接收器 / 浮窗没有页面可依附，硬造一个 `WindowManager` 浮层
就多一套要维护的东西，收益为零。

**代价（不藏）**：提示条仍然盖住页面底部约 40dp，2.6 秒后消失。这是浮层的固有属性，
换成它得到的三个好处是不跨页、不压系统权限框、位置可预期。

**测试怎么改的**（不是删）：

- `GuideTest.lockProbeHint_showsToastButDropsItOnPause` → `lockProbeHint_showsBarAndDropsItOnPause`：
  断言的还是同一件事（点完要有提示、`onPause` 要收走），只是从 `ShadowToast` 改成在 content 里找 `Hint.TAG`。
- `GuideTipTimingTest.rewatchFromSettings_saysUpdatedImmediately` → `rewatchFromSettings_handsTipToSettingsPage`：
  改成断言「存了、没退回 Toast、没塞 PendingTip」，并新增 `settingsPageShowsTheHandedTip` 验证设置页真的浮出来且取走即清。
- 新增 `HintTest` 七条：显示 / 替换 / 到时自动消失 / `cancel` / 页面关闭不加 / 非 Activity 退 Toast / pending 取一次即清。
- 反向验证两次：去掉「先摘旧条」→ 替换那条红；不判 `isFinishing` → 页面关闭那条红。

**还剩一个可见的不完美**：提示条压住的是「更多」这类分组标题时，视觉上仍算遮挡。

### D4 落地记录（4×3 的闹钟状态）

**当年为什么没有**：`5dfd025`（v1.0.2，2026-10-31）的提交说明写着「4×3 的标题行放不下
第三段，『闹钟已开启』在 250dp 宽里直接贴边，去掉」。当时 chip 是「大周 · 休 2 天」，
13sp 标题 + 长 chip + 10sp 闹钟，250dp 扣掉内边距只剩 226dp。

**为什么现在放得下**：v1.23.29 把 chip 收成「双休 / 上 2 休 2」（32dp），v1.23.32 把
框架字号钉住（不再随系统字体变宽变高）。重算：134 + 32 + 50 + 18 = 234 = 可用内宽，
标题本身只需 80dp，余 54dp。

**安全阀**：标题是 `layout_weight="1"`，宽度不够时先被压扁的是月份。`probe()` 在同一次
inflate 里用真文本摆一次，`titleRowFits()` 比较「分到的宽度 vs `measureText` 需要的宽度」，
判不过就收起第三段。只有极端周期会触发（12 天断成四段 → 「12 天一轮 · 上 6 休 6」）。

**坑**：判据依赖 `Paint.measureText`，在没有 `@GraphicsMode(NATIVE)` 的 Robolectric 里
只量出 11px，长文本会被误判成放得下——那条守门测试因此放在 `MonthWidgetFontScaleTest`。

### D1 落地记录（`RescheduleGuard`）

三处调用点（`AlarmReceiver` 响铃后与时钟跳变丢弃后、`BootReceiver` 开机 / 改时间后）
原来各写一份 `catch (Throwable ignore)`。现在统一走 `RescheduleGuard`：

- **失败留痕**：写 `Prefs.KEY_RESCHEDULE_PENDING`，并挂**一次** 60 秒后的重试
  （显式 Intent 回 `BootReceiver`，action `RESCHEDULE_RETRY`，不进 manifest，
  用 `ELAPSED_REALTIME` 挂，所以改系统时间不影响「60 秒后」）。
- **重试不续挂**：重试那次若再失败只留标记，不再挂新的。否则一个必然失败的排程
  会变成每 60 秒醒一次的后台闹钟，比原来的静默更糟。
- **第三道入口**：`MainActivity.onCreate` 里 `runIfPending`——设备长期不重启、期间也没有
  新闹钟时，用户打开 App 就会补排一次。

守门 `RescheduleGuardTest` 六条（失败留标记 / 成功清标记 / 60 秒后挂一次 /
重试不再续挂 / 无欠账不白跑 / 有欠账真排上并清标记）+ `BootReceiverTest.retryAction_reschedulesAndClearsMark`
（重试广播真能补排）。两次反向验证：去掉记账 → 两条精确红；无条件续挂 → 「不许链式续挂」精确红。

**这条真机验证不出来**：「跳日期 → 改回 → 明早仍响」只能证明正常路径没坏；
要复现缺口必须人为让重排抛异常，所以守门测试用可注入的 `Work` 造失败。

### D3 落地记录（`WidgetTextFit`）

**像素测量**（用户三张图，1200×2670 / density 3）。4×3 的「标签底 → 下一行数字顶」间隙：
110% 41px（13.7dp）、125% 31px（10.3dp）、**145% 只剩 19px（6.3dp）**；数字带高度
27 → 29 → 34px，与 fontScale 严格成正比。字按系统比例涨、格子不涨，最后两行字把行高吃满。

**合同高度下更糟**（Robolectric 真渲，250dp 宽 / 200dp 高 / 145%）：标签的 View 高 12px、
排版需要 43px，直接被压成一条。真机「看着还行」是因为启动器多给了 66dp（4×3 实际 266dp）。

**修法**：`WidgetTextFit` 按「这次更新拿到的卡尺寸」算字号上限——把布局真的摆一次量出
「一格多高、两行字要多少」（`MonthWidgetRender.measureCell`），判据是「一格上下留 6dp」，
装不下才收、下限 9 折。宽高取 `OPTION_APPWIDGET_MAX_WIDTH / MAX_HEIGHT`，拿不到退回 250 / 200dp。

**顺手挖出来的两件事**：
1. 老的 `MonthWidgetLayoutTest` 量的是**空格子**（静态布局 42 格都是 `text=""`），
   而空 TextView 的排版高度比有字时矮 8px（30 vs 38）——两条「不裁字」断言绿了几个月，
   其实什么都没测。已改成走 `RemoteViews` 渲染链路。
2. 4×3 在 provider 声明的 200dp 下，**标准字号本来就装不满一格**（33px 的格子塞 38px 的字），
   只是真机给了 266dp 才没露。现在一并收 9 折兜住。

守门 `WidgetTextFitTest` 10 条 + `MonthWidgetFontScaleTest` 5 条。
反向验证：`scale()` 直接返回 `fontScale`（取消收敛）→ 4 条精确红（3 条真渲 + 1 条算术）。
