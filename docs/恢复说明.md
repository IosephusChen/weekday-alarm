## 一、怎么拿到代码

**首选：克隆。** 仓库 2026-10-31 起是公开的，一条命令就够，不需要令牌、不需要任何包：

```bash
cd /workspace
git clone https://github.com/IosephusChen/weekday-alarm.git
```

克隆下来就是完整的一棵树——`AGENTS.md`、`PLAN.md`、`docs/` 全部、`tools/`、CI 配置都在里面，
**没有一样东西只存在于灾备包里**（唯一例外是 keystore，它本来就不许入库）。

两个已知的坑：

- **直连 `github.com` 偶发失败**，报 `GnuTLS recv error (-110)` 或 TLS 中断。**重试一次基本就好**
  （2026-11-06 实测：第一次挂，第二次成功）。别因为它挂一次就断定「沙箱不通外网」。
- 连着重试两次都不行，退到 `api.github.com` 取 tarball（这条链路在沙箱里更稳）：

  ```bash
  curl -sL -H "Authorization: Bearer $TOKEN" -o wa.tar.gz \
    https://api.github.com/repos/IosephusChen/weekday-alarm/tarball/main && tar xzf wa.tar.gz
  ```

  代价是**没有 `.git` 历史**：能读、能改、能跑测试，但推不上去（推要么 `git clone`，要么走
  `tools/push_via_api.py` 那套对象级接口）。

**兜底：灾备包。** 只在两种情况下用——断网（clone 完全不通），或者要**取回 keystore**。
包里是 `bundle`（离线只读仓库）+ `.jks` + `keystore.properties` + `签名凭据.txt` + 当时的 APK。

**第 1 步：解压灾备包，从 bundle 建仓库**

```bash
cd ~/work                                   # 随便一个空目录，下面几步都在这里
unzip -q 打工人闹钟-灾备包-*.zip              # 得到 备份-<日期>/（用通配，包名带日期，写死就过期）
git clone 备份-*/WeekdayAlarm-v*.bundle weekday-alarm
```

签名相关的两个文件（`weekdayalarm-release.jks`、`keystore.properties`）先留在备份目录里，
到第 3 步再复制就位——它们不属于「建仓库」，混在这里会让第 3 步看起来像多余的。

bundle 是单个文件的只读仓库，clone 出来就是完整历史（含 `docs/` 全部文档）。
校验：

```bash
cd weekday-alarm
git rev-list --count HEAD     # 与灾备包 恢复步骤.md 记的数字一致即可
git log --oneline -1          # 第一件事：对版本，旧包就说明灾备包过期了（见文首警告）
ls docs/                      # 应看到全部文档：md + 线框（数量会随版本增加，别背数字）
git status                    # 应干净
```

> 提交数故意不写在这里：本文件本身就在仓库里，写死一个数，下次提交就过期。
> 具体数字由灾备包里的 `恢复步骤.md` 记录（它在仓库外，生成时校验）。

**记得把 `origin` 改指 GitHub。** 从 bundle clone 出来的 `origin` 就是那个本地文件，
而 `tools/push_via_api.py` 靠 `git remote get-url origin` 解析 owner/repo，指错会直接退出
「看不懂 remote 地址：…/WeekdayAlarm-main.bundle」——恢复完不报错，等到要推的那天才发现。
改法是留着 bundle 当备用、另外加一条 GitHub 的：

```bash
git remote rename origin bundle
git remote add origin https://github.com/IosephusChen/weekday-alarm.git
```

不用配凭证，也不用 `credential.helper store`：推代码走 `tools/push_via_api.py`，令牌从
环境变量读，不落 `.git/config`（见 `流程规范.md` 第十三条的不变三条）。

**拉最新（只有走灾备包才需要；走 clone 的跳过，你拿到的就是 main）**

灾备包是离线快照，恢复出来天然是旧版本——20261102 那份停在 v1.0.11，落后二十个版本。

```bash
cd weekday-alarm
git pull --rebase origin main
git log --oneline -1     # 与 项目状态.md 第 1 节对得上，才算「最新」
```

**这一步不能跳。** 旧树上 `check_version.py` 也照样全通过——它只能证明「这棵树自洽」，
证明不了「这棵树是最新的」。跳过 pull 的后果是：在一份二十版前的代码上改东西，
改完推不上去（non-fast-forward），或者推上去了把别人的改动盖掉。
沙箱里 `github.com` 直连不稳（第七节），拉超时就重试一次；两次都不行，去 GitHub 网页
`Code → Download ZIP` 解到同一个位置，别将就着在旧树上开工。

**别拿整包 MD5 校验重构建的 APK。** 2026-10-26 实跑过两次：重构建出来的 APK 与包内那份
`unzip` 之后 `diff -rq` 零差异（`classes.dex`、资源、清单、连 `META-INF/CERT.RSA` 都全同），
整包 MD5 却不同。第二次拿 `cmp -l` 定位到差异起点 2,695,056 字节——正好在 APK Signing
Block（v2/v3 签名块）内部，两包长度、签名块起点、中央目录起点全都一模一样，差的只是
签名值本身（每次签名不同）。zip 条目的时间戳倒是固定的（Gradle 写成 1981-01-01，
可复现构建的常规做法），别把它当成原因。
要比就解包比内容。

文档进了仓库之后，改错可以 `git diff` / `git checkout` 回滚——v0.56.5 之前它们散在工作目录根、
没有任何版本历史，这也是它们反复失真的原因。

**第 2 步：补 `local.properties` 并检查环境**

```bash
cd weekday-alarm
# sdk.dir 写本机 SDK 的实际路径，这个文件不进仓库，必须自己建。
# 常见位置：$ANDROID_HOME、~/Android/Sdk、~/Library/Android/sdk、/opt/android-sdk
echo "sdk.dir=/opt/android-sdk" > local.properties

java -version                                        # 需要 17–21（Gradle 8.7 不支持 22+）
ls /opt/android-sdk/platforms                        # 应有 android-34
ls /opt/android-sdk/build-tools                      # 应有 34.0.0
```

缺 SDK 的话装命令行工具：

```bash
curl -sSL -o /tmp/cmdtools.zip https://dl.google.com/android/repository/commandlinetools-linux-11076708_latest.zip
mkdir -p /opt/android-sdk/cmdline-tools
unzip -q /tmp/cmdtools.zip -d /opt/android-sdk/cmdline-tools
mv /opt/android-sdk/cmdline-tools/cmdline-tools /opt/android-sdk/cmdline-tools/latest
yes | /opt/android-sdk/cmdline-tools/latest/bin/sdkmanager --licenses
/opt/android-sdk/cmdline-tools/latest/bin/sdkmanager "platform-tools" "platforms;android-34" "build-tools;34.0.0"
```

**第 3 步：放回签名密钥与口令**

```bash
cp 备份-*/weekdayalarm-release.jks .                             # 放到仓库的上一级
cp 备份-*/keystore.properties weekday-alarm/keystore.properties
keytool -list -keystore weekdayalarm-release.jks -alias weekdayalarm
```

keystore 必须放在**仓库的上一级目录**（与 `weekday-alarm/` 同级）——`keystore.properties`
里写的是 `storeFile=../weekdayalarm-release.jks`，以**仓库根**为基准解析（`app/build.gradle` 用
`rootProject.file(...)`）。换了摆放位置就要同步改这一行，否则 Gradle 报 keystore 找不到。
`keystore.properties` 已被 `.gitignore` 排除、不在仓库里，
所以两样都得从灾备包复制，**直接 `cp` 就位即可，不要手写**——里面已经是正确口令，
手写一遍反而容易把 `storePassword` 写成占位符导致签名失败。

上面那条 `keytool` 会提示输入口令（PKCS12 下 storePassword 与 keyPassword 相同，
口令在 `签名凭据.txt`，与仓库同级、不入库）。指纹必须是：

```
D4:17:FB:1F:96:87:D7:EC:F5:F8:4F:A4:69:AE:94:8D:6A:7D:BA:FC:7C:12:B9:94:F8:B0:15:8C:45:BD:B1:26
```

对不上就说明拿错了文件，装出来的包会报「签名不一致」，只能卸载重装、设置全丢。

> 公开仓库注意事项：**keystore 文件本身不在仓库里**（`.gitignore` 已排除 `*.keystore` / `*.jks`），
> `app/build.gradle` 是「本机有 keystore.properties 才用正式签名」，别人 clone 下来会回落到
> `~/.android/debug.keystore`，能装能测。想自己签，在 `signingConfigs` 里加一个指向你自己
> keystore 的 `release` 配置即可——密码与别名按你自己的填，别照抄本文的占位符。

**第 4 步：验证能构建**

```bash
cd weekday-alarm && ./gradlew testDebugUnitTest --console=plain 2>&1 | tail -20
```

**期望 0 失败**（条数以 `项目状态.md` 第 1 节为准——每发一版都会变，写死必然过期）。
这一条同时验证：JDK 通了、SDK 通了、依赖拉全了、代码完整。
首次构建要下载 Gradle 8.7 与依赖，5–15 分钟，**用 `run_in_background` 等，别用短超时**。
仓库已配好国内镜像：Gradle 走 `mirrors.cloud.tencent.com`，Maven 走 `mirrors.tencent.com`。

**沙箱坑：`~/.gradle/init.gradle`**。预置内容可能是坏的（`url https://...` 缺 `=` 和引号、
`mavelCentral()` 拼错），改好还会撞上项目的 `FAIL_ON_PROJECT_REPOS`——不能在 `allprojects{}` 里声明仓库，
只能在 settings 层注入：

```groovy
settingsEvaluated { settings ->
    def repos = settings.dependencyResolutionManagement.repositories
    repos.maven { url "https://mirrors.tencent.com/nexus/repository/maven-public/" }
    repos.google()
    repos.mavenCentral()
    def pluginRepos = settings.pluginManagement.repositories
    pluginRepos.maven { url "https://mirrors.tencent.com/nexus/repository/maven-public/" }
    pluginRepos.google()
    pluginRepos.mavenCentral()
    pluginRepos.gradlePluginPortal()
}
```

这段内容由迁移包的 `01-环境安装.sh` 第 5 步自动写入，**正常恢复不必手工改**。脚本是幂等的：
已写入过（文件含 `weekday-alarm-init-v1` 标记）就跳过；遇到别的文件先备份成
`init.gradle.bak.<时间戳>` 再覆盖，不会静默丢内容。手工改只用于没跑脚本、或脚本没走到第 5 步的场合。

**JDK 版本与 JIT 参数（2026-11-07 修订）**

`build.gradle` 的 `sourceCompatibility` / `targetCompatibility` 是 **17**，AGP 8.2.2 最低也要 17，
CI 用 Temurin 17——**本机也请用 17**。版本不齐时编译器行为会有细微差别，「我这儿是绿的」
换台机器就不成立，而排查这种事最费时间。

沙箱当前只有 Zulu **JDK 20**。**默认直接跑，不带任何 JVM 参数。**

2026-11-07 在 JDK 20 上实测（`--rerun-tasks --no-daemon`，同一个 workspace）：

| 命令行 | 耗时 | 结果 |
| --- | --- | --- |
| `./gradlew :app:testDebugUnitTest` | **94 秒** | 通过 |
| 带 `-XX:TieredStopAtLevel=1 -XX:ReservedCodeCacheSize=256m` | 121 秒 | 通过 |

带参数慢 27 秒，而且这一次并没有复现过去记录过的 SIGSEGV。所以那两个参数降级为
**对症下药**——只有真的看到 `SIGSEGV`，或 `SlideToStopTest` 报 MethodHandle 链接失败时才加：

```bash
JAVA_TOOL_OPTIONS="-XX:TieredStopAtLevel=1 -XX:ReservedCodeCacheSize=256m" ./gradlew testDebugUnitTest
```

真要加就两个一起给，缺一不可：只关 C2，C1 的产物会撑满默认 48MB CodeCache。
本机 / CI 一律不带。

## 二、灾备包里有什么、没有什么

| 内容 | 是否包含 | 说明 |
| --- | --- | --- |
| 完整源码 + `.git` 历史 | ✅ | 受控文件数与提交数见包内 `恢复步骤.md`（别在本文件写死，会过期） |
| 全部文档（md + 线框图） | ✅ | 在仓库 `docs/` 里，随 git 一起恢复 |
| `weekdayalarm-release.jks` | ✅ | **必须带**，签名不一致就无法覆盖安装 |
| `keystore.properties` | ✅ | **必须带**，否则构建回落 debug 签名，装不上手机 |
| 当前 APK | ✅ | 用户手机上要装的 |
| `local.properties` | ❌ | 写死本机 SDK 路径，按第 1 节自己建 |
| 历史 APK | ❌ | 都不在包里，都能从 git 重新构建 |
| `app/build/`、`.gradle/` | ❌ | 构建缓存，重新生成即可 |

包体几 MB（源码与历史 + 当前 APK + 说明与校验值），具体以生成为准。

**刷 bundle 的命令**（做灾备包/迁移包时）：

```bash
git bundle create WeekdayAlarm-main.bundle HEAD --branches --tags
```

`HEAD` 那个参数**不能省**。只写 `--branches --tags` 生成的 bundle 里没有 HEAD 行，
`git clone` 会报 `warning: remote HEAD refers to nonexistent ref`，检出的是空工作区——
包大小正常、md5 正常、`list-heads` 也列得出 23 个标签，看起来一切正常，实际一个文件都没有。
生成后务必验一次：

```bash
git clone WeekdayAlarm-main.bundle /tmp/check && ls /tmp/check   # 应看到 app/、docs/ 等
```

### 换证记录（别再换第三次）

| 代 | 文件 | 主体 | 状态 |
| --- | --- | --- | --- |
| 第一代 | `daxz-release.jks` | `CN=DaxiaoWeekAlarm…` | **已作废**（2026-10-27）。SHA-256 `A1:0D:49:E1…42:F6:FD`，签过 0.85.6 ~ 0.87.2 |

**为什么换**：v0.87.0 把包名与英文名统一成 Weekday Alarm 之后，第一代证书主体还写着
`DaxiaoWeekAlarm`，在系统「应用签名信息」里对不上。证书主体不可修改，只能重签。
选在 1.0 之前换，代价只是本人卸载重装一次；1.0 发出去之后再换，代价就是所有用户。

**代价（一次性，已付）**：0.87.2 及更早的包不能覆盖安装到 v0.87.3 上方，必须卸载重装。
卸载前先在旧包「更多设置 → 数据与桌面 → 导出配置」，装好新包再导入。

### 它保护的不是代码，是升级通道

**别把它当版权锁。** Android 的规则只有一条：同一个证书签的包才能覆盖安装。密钥在这里
起的作用，是对已装的 App 证明「这个新包确实出自原来那个作者」——代码谁都能照抄，但只有
这把钥匙能让**已经装了它的人继续升级**。

所以「重新生成一个就行」是错的。新证书等于一个新应用身份，Android 不认它和旧包的亲缘：

| 情况 | 后果 |
| --- | --- |
| **密钥丢了** | 所有已装用户（含你自己手机）永久停在 290。想升级必须卸载重装，**闹钟、班表、请假标记全部清零**。没有任何补救手段 |
| 密钥泄露 | 别人能签一个同包名的假包去冒充。免费、开源、不赚钱，都不改变这一点——**冒充不需要图利**，挂个广告或后门就够了 |

风险排序是**丢失 ≫ 泄露**。免费开源项目最容易在这里想反：「我又不靠它收钱，泄了也没损失」。
收不收钱，和「已装用户升不升级得上」是两件互不相干的事。

### 备份要求（三条都要满足，缺一条就不算备份）

1. **两处以上**，且至少一处不在这个沙箱里——沙箱重建就没了
2. **加密后再放**：网盘只当搬运工，放上去的是 7z / zip 密文，口令记在别处
3. **验证过才算数**：把备份取回来，按恢复包里的 `restore.py` 还原一次，要出 `已还原 4452 字节`，
   再核指纹对上。没验过的备份等于没有——「存了」和「存对了」从表面完全看不出来，
   只有出事那天才暴露

### 日常不需要把密钥带进沙箱

新会话是新沙箱，里面**通常没有** keystore——这是常态，不是故障。所以出包分两条路：

| 做法 | 沙箱里要有 `.jks` | 什么时候用 |
| --- | --- | --- |
| 手动 dispatch CI 的 `release` job | **不要**（Secrets 里有一份） | **正式发版的默认做法**：出包、验指纹、下载 artifact |
| 本地 `./gradlew assembleRelease` | **要** | 需要立刻拿到包、要真机装的时候 |

**没有 `.jks` 时别在本地出「正式包」。** `app/build.gradle` 在缺 `keystore.properties` 时会
落到本地 debug keystore——`assembleRelease` 照样 BUILD SUCCESSFUL，APK 也照常生成，只是签名
是 `androiddebugkey`。这种包装得上、跑得动，但**永远替代不了线上那一版**（签名不同，已装用户
覆盖安装会失败）。看着成功，实际等于没发。

## 七、多端：换一端开工

2026-11-06 起这个仓库不只一台机器在改（手机端、桌面端、网页 agent、CI）。**稳定的规矩在
`AGENTS.md` 第七节**——单写者、PR 交棒、`versionCode` 即锁。这里只留操作层的：谁能出包、
新会话先查什么、开工四步，以及几个网络与脚本上的坑（不数件数，数了下次就过期）。

**谁能出正式包，不看是哪一端，看这一端手里有没有 `.jks`。** 这个项目**没有固定主机端**：
2026-11-06 用户明确「随时会为了省积分开新会话，而每个会话都是新沙箱」。所以别按
「本机 / 云端」分，按 keystore 分：

| 端 | 出正式包 | 跑测试 | 独有价值 / 注意 |
| --- | --- | --- | --- |
| 任意 WorkBuddy 沙箱 | 能，但**默认不在这里出** | 直接 `./gradlew`，别加 JIT 参数 | 改代码 + 跑测试 + 真机截图对比；沙箱通常没 keystore，出包走 CI |
| Trae 桌面端 | 能，但**不建议** | 直接 `./gradlew`，不带参数 | 完整 diff、重构、调试；**工作区每次会话重建，见下** |
| GitHub Actions | 能，**不依赖本地任何状态** | 原生 JDK 17（跑的就是全量单测） | 换会话也照样出包；第三方裁判；手动触发可产签名包做验收 |
| 网页 agent | **不能** | 一般跑不了 Gradle | 只读审查、补文档、review PR |

CI 用的 Secrets 是 `KEYSTORE_BASE64` / `KEYSTORE_STORE_PASSWORD` / `KEYSTORE_KEY_ALIAS` /
`KEYSTORE_KEY_PASSWORD`。**CI 是唯一「换会话也照样能出包」的路**——它不读本地任何东西。

### keystore：默认就是没有，别当成故障

**新会话 = 新沙箱 = 空盘。** 所以 `../weekdayalarm-release.jks` 默认不存在，这不是环境没配好，
是常态。只有「要在本地立刻出包」才需要它；改代码、跑测试、开 PR、发版（走 CI）都不需要。

```bash
ls -l ../weekdayalarm-release.jks      # 有 → 能本地出包；没有 → 走 CI，别去恢复
```

四条记住：

1. **别假设它在，也别因为它不在就以为坏了。** 空沙箱里它就是没有。
2. **不在也不等于要重新生成。** 新证书 = 新应用身份，全体已装用户必须卸载重装。
   真需要就在发版包里取（第三节），别再生成第三把。
3. **任何「上次会话留下的东西」都不可假设存在**：仓库、分支、未推送的提交、临时目录里的 `.jks`、
   环境变量、`~/.gradle` 缓存。反过来——**进过 git（push 或 PR）、或写进本文件的东西，才活得下来**。
4. **要「换会话也能出包」，只有 CI 的 Secrets 那条路**不依赖本地任何状态。

**Trae 的工作区是每次会话重建的，不是同一个克隆延续下来。**（2026-11-06 实测：第二轮会话里
本地 `fix/ci-pin-runner` 分支连同上一轮的提交一起消失，当前分支变成一个新的 `trae/agent-XXXXXX`。）
它每次还会自动建一个 `trae/agent-XXXXXX` 本地分支，**没推送的东西会话结束就没了**。

两条推论，都别忘：

1. **在 Trae 上干活，做完立刻 push。**「产出必须进远端」在它这里不是规矩，是物理必然——
   不推就是丢。做完的直接进 main，没做完的开 PR 留在远端。
   `trae/agent-dNvTiA` 当年能活下来被发现，恰恰因为那一次它 push 了。
2. **别让 Trae 持有 keystore。** 工作区会重建，按第三节恢复的 `.jks` 下次会话可能连同临时目录
   一起没了，而恢复过程本身会把密钥落到某个陌生路径。同理：**任何临时沙箱都不是 keystore 的
   归宿**，出完包就该按第三节的备份口径确认它还有备份，而不是指望它下次还在。
3. **要「换会话也能出包」，只有两条路**：CI（Secrets），或者先按第三节还原 keystore。
   没有第三种——「上次那个沙箱里的 `.jks`」不算。

**开工前四步**（任一端都适用）：

```bash
git pull --rebase                  # 1. 这棵树是不是最新（versionCode 被另一头占掉就是在这发现的）
git config user.name               # 2. 有值吗？沙箱默认不带身份，首次 commit 会直接失败
python3 tools/check_version.py     # 3. 十秒确认版本与六处文档自洽，不需要 Gradle
grep -A2 '^## 七' AGENTS.md        # 4. 确认当前写者是谁、有没有在飞的版本
```

**「沙箱里直连 `github.com` 不通」这个旧结论作废。** 2026-11-06 实测：在空目录里 `git clone`
一次失败（`GnuTLS recv error (-110)`）、**重试一次即成功**；随后 `git push` 到一个临时分支
**不用手动贴令牌就推上去了**（沙箱自带 credential helper，`gh` 也是登录态），验完已删。

所以正确的说法是「**不稳，重试一次再说**」，不是「不通」。真要绕路时才上 `push_via_api.py`
（走 `api.github.com`）——别一上来就绕，那条路要逐对象重建，慢且限制多
（推不动 `.github/workflows/` 下任何文件，除非有 `workflow` scope）。

**CI 现在会替你裁判版本一致性**（`.github/workflows/android.yml` 的 `version` job，跑的就是
上面第 2 步那个脚本）。所以改完文档忘了同步版本号，PR 阶段就会红——不必等出包那天。

**`tools/push_via_api.py` 推完会把本地 `origin/main` 一起对齐**（2026-11-06 加的）。
此前它只动远端 ref、不动本地跟踪 ref，`git status` 会一直显示「领先 N 个提交」，
`tools/release.sh` 的写者自检也算错位。

**但有一种情况它对齐不了**：在网页上改过文件之后。网页提交那个 SHA 本地永远不会
有——git 的 SHA 里含着 committer 时间戳，那个时间戳是 GitHub 服务端写的，逐字节还原
不出来（试过用 patch 里的 `Date:` 行还原 author 的时区，committer 那一半仍对不上）。
所以「本地和远端内容完全相同、SHA 不同」是**常态**，不是异常。

脚本为此分了两条路（`tools/push_via_api.py` 文件头有完整说明）：

| 本地有没有远端那个提交 | 校验到什么程度 | 推完怎么对齐 |
| --- | --- | --- |
| **有**（平时、本机 `git pull` 之后） | 逐提交重建，**commit SHA 必须相等** | 本地 `origin/main` 直接指过去 |
| **没有**（网页改过文件） | tree 必须相等、每个 blob 的 SHA 必须相等、父链必须连续，只放开 commit 自身那一个 SHA | 记进 `.git/push_via_api.state`（本地 SHA ↔ 远端 SHA），下次从这条对应关系续推 |

代价要知道：走第二条路之后，`git status` 会一直显示「领先 N 个提交」，那是哈希差异、
不是内容差异。想彻底消掉，只有换一台能直连 `github.com` 的机器 `git pull --rebase`，
让本地真正拿到那些对象。

**顺带记一个排查陷阱**：令牌缺 `workflow` scope 时，任何会改到 `.github/workflows/`
的 tree 请求都返回 **404**（不是 403），同一批其他路径全是 201。看着像仓库或路径不
存在，实际是权限问题。脚本现在会把这种 404 翻译成明确提示；碰上它只有两条出路——
网页上改，或换一个带 `Workflows: Read and write` 的 fine-grained PAT。
