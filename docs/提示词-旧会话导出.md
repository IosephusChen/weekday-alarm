# 提示词：从旧会话导出工程材料

> 用法：整段复制下面「提示词正文」里的内容，粘贴到 v1.19.7 之前那个会话窗口，发送。
> 它会分三段输出，你把结果原样贴回新会话即可，格式乱不要紧。

---

## 提示词正文（从下一行开始复制）

这个项目现在叫「打工人闹钟」，**早期叫「大小周闹钟」**——同一个 App，Android，
包名 `com.daxz.weekalarm` 从头到尾没变过，改名发生在 v1.22.0。按这两个名字一起回忆。

它早期没有留更新日志，我需要你回看本会话，整理出三份材料。请**分三段输出**，
每段以 `### 一`、`### 二`、`### 三` 开头，段与段之间不要夹解释性的话。

### 一、早期版本记录（最重要，先做这份）

范围：**v1.0 到 v1.19.6（versionCode 1~41）**。v1.19.7 及之后我已经有了，不要重复。

格式：Markdown 表格，按时间从早到晚。

| versionCode | 版本号 | 一句话标题 | 要点（2~3 条，用 / 分隔） |

规则：

1. 标题写「做了什么」，不要写「优化体验」「修复若干问题」这类空话
2. 版本号或 versionCode 记不清就**留空**，绝对不要猜、不要编号凑数
3. 一次打包改了好几件事的，合成一条，不要拆成多条
4. 只写代码真的改过、打过包的版本；纯讨论没落地的不要写
5. **当时的叫法照旧写**（那段时间应用名是「大小周闹钟」，「大小周」就是当时的制度名），
   不要替换成现在的说法——记录要还原当时的样子

### 二、真机测试踩过的坑

格式：Markdown 表格。

| 现象 | 设备 / 系统 | 原因 | 怎么解决的 |

规则：

1. 只写**在真机上实际出现过**的问题，不要写推测和「可能」
2. 原因或解法记不清就写「不详」
3. 至今没解决的，在表格最后单独加一行「**仍未解决**：…」
4. 本会话里没有任何真机测试记录，这一段就写「无记录」，不要编

### 三、被否决或搁置的想法

格式：Markdown 表格。

| 想法 | 结论（否决 / 搁置） | 原因 |

规则：

1. 包括你提出但用户没采纳的，也包括用户提过但被我否掉的
2. 原因记不清就写「不详」
3. 只写**真的讨论过**的，不要写「以后也许可以」这种没发生过的

---

三份都要。如果某一份在本会话里确实找不到依据，就明说「本会话无相关记录」，
不要用常识补全。**宁可交一份有洞的材料，也不要交一份编的材料。**

如果本会话的上下文已经不完整、回忆不可靠，请在第一段开头加一句
「注意：本会话上下文可能已被压缩，以下内容置信度有限」，然后再输出。

---

## 使用说明

| 情况 | 怎么办 |
| --- | --- |
| 三段都出来了 | 原样贴回新会话，我负责整理、去重、转成 `Changelog.java` 格式 |
| 只出来了第一段 | 也行，先贴第一段。第一段最重要，二、三段是添头 |
| 它开始编版本号 | 提醒它「记不清就留空」，或者直接把它编的部分删掉再贴给我 |
| 输出被截断 | 分两次要：「先给第一段，我给完再要第二段」 |

**为什么写这么细**：旧会话的 AI 会有强烈的「补全」倾向——你问 41 个版本，它
凑不出 41 条就会开始编。上面那几条规则（留空、不详、宁可少列）都是堵这个的。
