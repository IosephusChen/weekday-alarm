### v0.89.5（versionCode 214）— 两项权限的说法统一了

2026-10-29。用户看完 0.89.4 的权限页，只说了一句：「后台弹出界面和锁屏显示文案统一一下」。

**一、两行指的是同一个地方，却写成了两种。**

| 行 | 当时的写法 |
|---|---|
| 后台弹出界面 | 去开启 · 进去点「其他权限」 |
| 锁屏显示 | 去开启 · 在「其他权限」里 |

点进去是同一个页面——`ACTION_APPLICATION_DETAILS_SETTINGS` 落到「应用信息 → 权限」，
两项都在下一层的「其他权限」里。说法不同，读起来像要跑两个地方开两个不同的东西。
其中「进去点」是 v0.58.3 为后台弹出写的（那时它确实藏在下一层），「在…里」是
v0.89.4 为锁屏显示写的。两句话各自都正确，放一起就矛盾了。

**二、改法：抽常量，而不是把两句抄成一样。**

只把字改齐，下次谁再调整其中一行，又会分叉。所以位置文案收成一个常量
`HINT_OTHER_PERMS`，两行都引用它——物理上不可能不一致。

顺带把锁屏显示的副标题里「这一项在「其他权限」里」删掉：位置已经在状态行说了一次，
副标题只讲后果（「锁屏时看不到响铃界面」）。两行的结构也就此对齐：**副标题讲代价，
状态行讲去哪开**。

**三、守住。**

新增 `permissionRows_shareOneLocationHint`：源码级断言，`GuideActivity.java` 里不许再
出现「进去点「其他权限」」这个写法，且 `HINT_OTHER_PERMS` 至少被引用三处（定义 + 两行）。
界面断言摆不平这件事——那两行由 `refreshPermissions()` 运行时写入，显示「去开启」还是
「已开启」取决于 FSI 权限的当前值，Robolectric 里不好造。

732 条测试，0 失败。

### v0.89.4（versionCode 213）— 「锁屏显示」那行指错了地方

2026-10-29。用户按图索骥找过去，发现那一页里根本没有「锁屏显示」。

**一、错在哪。**

权限清单底部那行写的是「去开启 · 同上一页」，副标题还补了一句「和自启动在同一页」。
但上一行是「自启动」，点进去是「自启动管理」（一个应用列表，打工人闹钟在列表中），
里面没有任何一项叫「锁屏显示」。它真正的家在「其他权限」里。

**二、为什么错。**

v0.73.5 之前，这一行紧跟在「后台弹出界面」下面，两行同在小米的权限编辑页，
所以「同上一页」指的就是「后台弹出界面」——没错。v0.73.5 把这一行移到了底部
（自启动之后），**文案没跟着动**。移一次位置，一句话就变成了谎话。

**三、改法。**

状态行：「去开启 · 在「其他权限」里」——直接说位置，不用相对方位词。
副标题：「……解锁才出现。这一项在「其他权限」里。」——删掉「和自启动在同一页」。

正式的名称比方位词靠谱：方位词依赖布局顺序，改一次布局就得改一次文案，
而布局是最容易被「顺手调一下」的东西。

### v0.89.3（versionCode 212）— 精确闹钟那行，平时收起来了

2026-10-29。v0.89.2 发出去半小时后，用户问：「既然默认是开启的，权限页是不是可以删掉这一条？」

**这个反问是对的，但不该删。**

真机（Android 16 + 澎湃）上，这一项是 `USE_EXACT_ALARM` 给的：安装即授予，系统页那个开关
开着而且是灰的，点不动。App 里写「已开启 · 到点精确到秒」，等于按天重复一句用户既改不了、
也无需知道的话。这正是 v0.58.3 删掉它的理由，那一半判断今天仍然成立。

不成立的是另一半：`USE_EXACT_ALARM` 是 Android 13 才有的权限。Android 12 上只有
`SCHEDULE_EXACT_ALARM`，而它**用户可以关**。关掉之后闹钟会晚最多 1 分钟、状态栏也没有
图标，用户没有任何途径看出来。删掉这行，等于把这批人留在沉默里。

**所以改成：给到了就藏起来，没给才出现。**

平时不占位置，出问题时不沉默——和「自启动」那行写「系统读不到 · 点开自查」是同一个原则：
不知道就说不知道，没事就别占地方。

分隔线跟着一起隐藏（单独给 `divider_exact` 加了 id），否则会留下一条孤零零的横线。
顶部那句「前四项会打勾」也改成不数数的「这几项」——第四项现在可能不在场上。

### v0.89.2（versionCode 211）— 精确闹钟没开，现在看得见了

2026-10-29。用户装机后问：「锁屏界面不显示闹钟，正常吗？」

**一、先分清两件事。**

锁屏时钟下面那行「明天 07:00 闹钟」，是系统时钟应用在锁屏上的特权展示，第三方应用做不到，
我们本来就没有。但截图里还有一个更实在的东西：**状态栏左上角连小闹钟图标都没有**。
这个图标是 `setAlarmClock()` 的产物，系统代画，跟我们的界面无关。

**二、图标为什么没了。**

`ScheduleManager.setAlarm()` 原本这样写：

    if (canScheduleExactAlarms(ctx)) {
        am.setAlarmClock(...);            // 有图标，精确到秒
    } else {
        am.setWindow(..., 60_000L, pi);   // 无图标，最多晚 60 秒
    }

图标缺失说明走进了 else。而 `canScheduleExactAlarms()` 只是「系统认为你该不该有」的预判，
不是硬拦截——部分 ROM 对侧载包报 false，实际仍放行 `setAlarmClock`。改成不预判、直接调，
被系统拒绝后再降级：代价只是一次被拒的调用，换回的可能是一个图标和 60 秒精度。

**三、v0.58.3 删过这一行，理由是错的。**

当年「新手引导 → 权限」里有一行「闹钟和提醒」，v0.58.3 删掉了，理由写得很有信心：
声明了 `USE_EXACT_ALARM`，Android 13+ 安装即授予、用户关不掉，留一行只能点进去还改不了的，
只会让人以为哪里没设置好。

真机（Android 16 + 澎湃）推翻了这个前提：系统设置里既没有「闹钟和提醒」，也没有任何能改的
开关，而权限实际没给到。**界面保持沉默，等于让用户永远查不出「为什么我的闹钟晚了一分钟」。**
所以这一行加回来，职责改了：不是让用户去改一个改不了的开关，是**把看不出来的状态显示出来**
——开了写「到点精确到秒」，没开写「可能晚 1 分钟，状态栏也没有闹钟图标」。

顺手接上从没被调用过的 `PermissionGuides.requestExactAlarm()`：它写好很久了，但没有任何
入口指向它，等于一段注释。

**四、钉住。**

`ScheduleExactAlarmTest` 检查 `setAlarm()` 里不再出现 `if (canScheduleExactAlarms`。
Robolectric 的 `ShadowAlarmManager` 把 `setAlarmClock` 记成普通的 `RTC_WAKEUP` 闹钟，
行为测试分辨不了两条分支，只能看代码长什么样。
`GuideTest` 里原本守着「这一行必须不存在」的断言，改为「存在，且开与没开两种文案都要说清」。

### v0.89.1（versionCode 210）— 通知卡片自己带底色

2026-10-29。v0.87.7 修过一次「深色锁屏标题消失」，四天后又复发，这次改的是根子。

**一、v0.87.7 的假设错了。**

那一版认为「通知卡片的底色跟系统深浅走」，于是按 `Resources.getSystem().uiMode` 挑白字
或近黑字，还专门加了一条源码钉子防止改回 `ctx.getResources()`。

2026-10-28 22:42 用户发来截图：系统是深色模式，睡前提醒的标题「明天要上班」却是近黑
（`0xFF1E2235`），压在深紫卡片上几乎看不见；正文「明早 07:00 起床」也是浅色那套灰。

**二、真机上的机制跟假设不一样。**

通知一旦 `setColor`，部分 ROM（小米、ColorOS 等）会把整张卡片按这个色做 colorized
染色——**底色由这个颜色决定，与明暗模式无关**。而 App 进程里读到的 `uiMode`，还可能
被 HyperOS 的「单个应用深色」覆盖影响。两个变量都不受我们控制，任何「按某个信号判断
底色」的写法，都只是把一个 bug 换成另一个。

**三、否掉的方案。**

1. 换判断源（`UiModeManager.getNightMode()`）——只能覆盖「手动深色/浅色」，
   定时深色返回 `MODE_NIGHT_CUSTOM`，还是得回落到 `uiMode`，等于没修。
2. 去掉 `setColor`，让系统不染色——赌 ROM 行为，换台手机可能又糊。
3. 文字改用半透明叠加——浅色卡片上 40% 黑只能到 2.6:1，达不到 4.5:1 的正文标准。

**四、最后做的：把底色收回自己手里。**

卡片自己画品牌紫渐变（`bg_notif_card`，hero_start → hero_end），文字定死白色。
系统染不染色、深浅怎么切，文字永远压在这块紫上，对比度恒定：标题 6.3:1、正文 5.2:1
（WCAG AA 要求 4.5:1）。

配套改动：去掉四处 `setColor`（否则紫上叠紫）、次操作药丸的描边从 violet 换成 60% 白
（紫描边压在紫底上会融掉）、`NotifTheme` 从「按模式挑色」退化成四个常量。

**五、这次留的钉子不一样。**

旧钉子检查「有没有读对数据源」；新钉子检查「有没有又想猜」——源码里出现 `uiMode`
或 `getConfiguration` 就红。另外加了一条布局钉子：两个通知布局都必须挂着
`@drawable/bg_notif_card`。白字一旦失去紫底，就是白字压白卡片，比原来的 bug 更彻底，
而单元测试看不到像素，只能从布局里查这一行。

### v0.89.0（versionCode 209）— 「关于」页可以检查更新

2026-10-28。代码要推 GitHub 了，用户问「能不能连 GitHub 更新」。讨论了几轮才动手，
中间否掉过两个方案，记在这里免得以后重走一遍。

**一、只做到「检查 + 交给浏览器下载」，不做应用内下载安装。**
应用内下载要多一个 `REQUEST_INSTALL_PACKAGES` 权限，还要引导用户去系统设置里开
「安装未知应用」，装的时候小米还会再拦一次「风险应用」。换来的是省掉「切浏览器」
这一步——用户点击次数从 8 次降到 6 次，而纯检查 + 跳转也是 6 次。花一天半换零收益，
还要自己处理断流、装完进程被杀、切走 App 回来弹窗消失这些说不清的问题。
更关键的是：**下载走 GitHub 的 `objects.githubusercontent.com`，国内本来就慢**，
自己写的下载没有断点续传，浏览器有。把它交给浏览器，损失最小、责任最清。

**二、数据源不用 `api.github.com`，用仓库根的 `version.json`。**
GitHub 的 REST API 未认证时按 IP 限流 60 次/小时，出口 IP 被邻居打满就全部 403；
国内连通性也时好时坏。改成静态文件走 jsDelivr + raw 双源，和节假日数据同一套通路
（已经验证过国内可用、30–40ms），几百字节、没有限流。
**代价写在明处**：jsDelivr 会缓存 `@master` 约 12 小时，刚发版那半天自己可能查到旧值。
这是 CDN 的固有行为，不修——真急着验，用 raw 那个源。

**三、比 versionCode，不比 tag 字符串。**
主流写法是拿 `tag_name` 做字符串比较，遇到 `0.87.10` 和 `0.9.0` 会判反。整数没这问题。
代价是 `version.json` 必须跟着 `build.gradle` 走——所以它由 `tools/release.sh` 从
`Changelog.java` 首条自动生成，并且有一条测试盯着两者相等（`UpdateCheckerTest`）。
忘了跑脚本就改版本号，直接红。

**四、查到新版不弹任何东西。**
只把结果写进 Prefs，用户下次打开「关于」页时那一行自己变成「v0.89.0 可更新」。
启动路径上弹更新框是最招人烦的一类打扰，而更新又不像「明早响不响」那样非知道不可。
节律也是照这个思路定的：成功过 7 天一次，失败过隔天一次。失败不降频的话，一次断网
就要等一周才有下次机会，用户会以为功能坏了。

**五、APK 直链只认 GitHub 的域名。**
`version.json` 里的 `apk` 字段必须以 `https://` 开头、host 落在 `github.com` /
`githubusercontent.com` 上，否则整个字段作废、按钮退化成「去发布页」。
这不是防篡改（真被改了也装不上，签名对不上；这一层是 Android 系统给的），
而是防止 `intent://` 之类的伪协议被 `ACTION_VIEW` 消化成任意组件跳转。
一个只用来下载的字段，没理由接受任何别的 scheme。

另外两条配套：**APK 在 Release 里用 ASCII 文件名**（`weekday-alarm-0.89.0.apk`），
中文名在 URL 里编码后部分浏览器会存成乱码文件，用户找不到装哪个；
**「关于」页那行的值不在打开页面时现查**，静默检查的结果落在 Prefs 里，界面只读——
打开页面不该挂一次网络往返。

顺带把隐私说明改了：网络请求从「只有节假日数据」变成「两处」，都只带版本号作标识。

### v0.88.0（versionCode 208）— 每条闹钟可以选自己的铃声

2026-10-28。用户提的：设置里选的是**默认铃声**，新建闹钟时想单独选一个。
讨论后定下三件事，下面每件都有代价，写清楚免得以后改回去。

**一、默认值是 null（跟随设置），不是新建时抄一份当时的铃声。**
如果新建时把「设置里此刻的铃声」抄进闹钟，用户之后换默认铃声，老闹钟不会跟着变——
变成「我明明换了，怎么还是旧声音」。所以只有用户在这条闹钟里主动选过才落盘，
`Alarm.toJson` 里也是「非空才写」，老备份没有这个键，读进来自然是跟随。

**二、选择器有三个状态，不能合并成两个。**
`null` 原本已经表示「系统默认铃声」（设置页那套）。单个闹钟又多出「跟随设置」——
如果两者都用 null，用户给闹钟选了「系统默认」，结果却跟着设置走，就说不清了。
所以 `RingtoneDialog` 加了一个带 `followSetting` 的回调：第一项「跟随设置（清晨）」、
第二项「系统默认」、之后才是铃声列表。设置页仍走旧的两态入口，行为不变。

**三、播放三级回落：闹钟自己 → 设置 → 系统默认。**
`AlarmService.resolveRingtoneUri(ctx, alarmId)` 拆成静态方法便于测。
按 id 查不到闹钟（响铃期间被删）或 URI 解析失败，都往下落，不会不响。
选铃声只枚举系统媒体库的闹钟铃声，不碰本地文件，所以没有持久读权限那套麻烦。

**换设备的坑**：`content://media/internal/audio/media/123` 在另一台手机上可能是别的歌，
也可能不存在。播放有兜底，编辑器那一行会显示「原铃声不可用，将用默认」，
不再用「已选铃声」糊弄过去（那个文案本来是给取不到标题的情况用的）。

**其他**：复制闹钟时铃声一起复制（和颜色一样，复制的是完整内容）；
备份导出/导入随闹钟数组自动来回，不用改格式。

**测试**：714 条（+13），0 失败。覆盖 JSON 往返、默认值不落盘、空串归一、
三级回落、复制保留、编辑器默认显示「跟随设置」、编辑不碰铃声不被洗掉。

### v0.87.7（versionCode 207）— 深色锁屏上，通知标题不再消失

2026-10-28。用户截图：深色锁屏上，睡前提醒的标题「明天要上班」几乎看不见，
只剩正文勉强能读。

**根因：拿 App 的深浅当通知栏的深浅。**
`NotifTheme` 判断明暗读的是 `ctx.getResources().getConfiguration().uiMode`——
那是 **App 自己**的配置。而通知卡片的底色是 SystemUI 画的，跟**系统**深浅走。
两者通常一致，所以这个 bug 藏了一年多；直到用户把本 App 单独设成浅色
（HyperOS「深色模式 → 单独的应用」），App 是日间、锁屏是深色，
于是深色卡片上落了 `#1E2235` 的近黑标题、`#6B7189` 的中灰正文。
截图取样：卡片底 `#2A2A2A`，标题亮度只有 30 左右，等于没写。

**修复**：判断改读 `Resources.getSystem().getConfiguration()`，只问系统。
`title()` / `text()` 也不再收 `Context`（除了强调色要取资源），
免得下一个人以为「传谁的 context 就按谁的深浅」。

四条通知（提前提醒、响铃、稍后再响、睡前提醒）共用 `NotifCard.build`，
改一处全好；提前提醒的横幅走 `PreNoticeReceiver.theme`，同一批色值。

**测试**：701 条（+5），0 失败。新增 `NotifThemeTest`：
深色给白字、浅色给近黑字、两种卡片底上对比度都 ≥ 4.5，
外加一条源码钉子——`NotifTheme` 里出现 `ctx.getResources()` 就红。
（行为测试兜不住这个：Robolectric 里 App 与系统共用一套 qualifiers，
「读 App」和「读系统」永远同答案，只有看源码才分得出来。）

### v0.87.6（versionCode 206）— 「这次不响」不再误伤同一天的新闹钟

2026-10-27。v0.87.5 上线几小时后自查出来的两个漏洞，同一个根因：
**跳过标记用「alarmId + 日期」当身份，而 alarmId 不是稳定身份。**

**缺陷一：删光闹钟再重建，新闹钟当天不响。**
`nextAlarmId` 取「现有最大 id + 1」，删光必然回到 1；新建的 id=1 正好撞上
残留的 `1:今天`，重排时被跳过。表现是：列表里开关开着、时间是新的、
主页却没有「下次闹钟」，今天就是不响——用户完全无从理解。

**缺陷二：点完「这次不响」再改时间，当天仍被跳过。**
`AlarmEditor.applyEdit` 里有明确的一行 `enabled = true`，注释写着「改完就开」，
但编辑复用同一个 id，跳过标记还在——「改完就开」被标记推翻，
开关开着、时间也对、就是不响。

**顺带**：`pruneSkipOnce` 排在 `if (alarms.isEmpty()) return 0;` 之后。
删光闹钟那一刻正好走 return，过期标记永远清不掉。既是数据泄漏，
也是缺陷一能成立的帮凶。

**修复**：

| 改动 | 位置 |
| --- | --- |
| 闹钟 id 改持久递增（新增 `alarm_id_seq`），永不复用；取「计数器与现有最大值」的较大者，兼容旧数据 | `Prefs.nextAlarmId` |
| 编辑保存时作废该 id 的跳过标记 | `AlarmEditor.applyEdit` |
| 列表里关掉再打开 = 重新启用，同样作废 | `MainActivity.toggleAlarm` |
| `pruneSkipOnce` 提到 `isEmpty` 之前 | `ScheduleManager.rescheduleAllLocked` |

**测试**：692 条（+4 回归钉子：删光重建 id 不回头、清标记不连坐 id=12、
改时间解除当天跳过、删光后 prune 仍执行），0 失败。lint 0 errors。

**文档**：冻结点 key 表补上 `legacy_scheme_cleaned`（v0.87.2 加了测试漏了文档），
计数从「40 个」改成与实际一致的 43。

### v0.87.5（versionCode 205）— 「这次不响」不再被重排复活

2026-10-27。真机验证撞出来的第二个 bug，这次有完整的现场录像（三张截图）。

**现象**：13:13 对 13:54 的闹钟在提前提醒通知上点了「这次不响」；
13:40 午休闹钟一响，13:54 的实例连同预告通知一起复活——用户在锁屏上亲眼看到
「闹钟 即将响铃 13:54 响铃」重新挂出来。点了的取消只活到下一次响铃为止。

**根因**：「这次不响」（`cancelThis`）只撤已注册的系统闹钟实例，不留任何
"这次已跳过"的记录。而 `AlarmReceiver` 在每次响铃后都会跑一次全量重排
（先取消全部、再按当前列表原样重设），列表里开关还开着，实例就被原样排回去。
改设置、重启手机、变时区也会同样复活。单闹钟时代"点完到响铃之间没有别的响铃"
掩盖了它，多闹钟 + 窗口内点按就现形。

**修复**：

- `Prefs` 新增 `skip_once`（元素 `alarmId:yyyy-MM-dd`，进冻结表）：
  「这次不响」写入，重排的候选收集跳过标记中的实例，日期一过自动失效；
- 取消后立即在后台对齐一遍状态：重排（认标记，不会复活）+ 刷小组件，
  主页倒计时与列表不再有"看不见的迟到"；
- **仅一次的闹钟**没有"明天"，跳过这一次后就是僵尸开关（永远不响却显示开启），
  「这次不响」直接把它的开关关掉；每天 / 仅上班日的闹钟保持只跳过、不动开关。

**测试**：688 条（+2 回归钉子：跨重排不复活 + 仅一次关开关每天不动），0 失败。
lint 0 errors。

### v0.87.2（versionCode 202）— 闹钟内部标识换成 `weekdayalarm://`

2026-10-27。用户问「改了有什么后果」之后决定改。

**改的是什么**：闹钟用 URI 的 scheme 原本是 `daxz://`，现在统一成 `weekdayalarm://`
（6 种形式：alarm / prenotice / autostop / snooze-cancel / bedtime / bedtime-skip）。
它对用户完全不可见——不显示、不进备份、不进网络请求，只用来让不同的 PendingIntent
不互相覆盖。改它的唯一理由是**项目里不该留没人说得清来历的标识**，
和昨天把包名从 `com.daxz.weekalarm` 换成 `io.github.iosephuschen.weekdayalarm` 是同一件事。

**为什么不能只改字符串**：`AlarmManager` 靠 PendingIntent 的 component + action + data
三项匹配来取消，scheme 一变，`am.cancel()` 就打不中旧实例。而它们是一次性闹钟，
会一直躺在系统里到各自到期——期间每天多触发一次（服务幂等，不会双铃，但会
「响了一下又从头开始」），还挤占 ROM 的 500 个闹钟名额。

**解法照抄 v0.23.0**：那时 requestCode 编码从「相对今天」改成「绝对日期」，也踩过同一个坑，
留下了 `cancelLegacy()`。这次加 `cancelLegacyScheme()`，同样的套路——
`FLAG_NO_CREATE` 只查不建，查不到就跳过；用 `Prefs.KEY_LEGACY_SCHEME_CLEANED`
标记「只做一次」，避免每次重排都白查几百次 IPC。

**测试**：688 条（+3）0 失败。新增 `SchemeMigrationTest` 三条：新注册的每个实例
都用新 scheme、旧 scheme 的残留能被 `cancelAll` 清掉、清理标记只置一次。

> 第三条测试我做过一次反向验证：把 `cancelLegacyScheme` 的调用临时注释掉，
> 测试确实变红——这说明它抓到的是行为，不是巧合。

#### 顺手修掉的一个测试环境坑（v0.76.0）

写 UI 守门时撞上一个「隔离跑全绿、全套跑随机红」的怪事，探针定位到根因：
**单元测试会真的连网**。`App.onCreate` 的节假日自动检查（`HolidayUpdater.check`）跑在后台线程上，
而 `HolidayData` 的远程层是**静态、整体替换**的——后台线程落地时会 `REMOTE.clear()`，
把同一 JVM 里正在跑的测试自己注入的数据冲掉。全套测试里有 6 个测试类用 manifest 里的真实
`App`，它们的后台拉取线程会活到下一个测试类运行。

**修法**：`App.onCreate` 的自动检查加 `!BuildConfig.DEBUG` 门（debug 构建跳过；用户装的
release 不受影响），并在 `build.gradle` 显式开 `buildConfig true`（AGP 8 起默认不生成）。
从此单元测试完全不碰网络——这类「随机红」以后不会再有了。

### v0.73.3（versionCode 155）— 修七个静默 bug，设置页文案说人话

**七个 bug 全是「编译过、测试绿、真机上坏」的静默缺陷**，按严重程度：

**为什么是并排而不是上下两行**：4×2 的组件高度经不起再加一行，硬加会把七格班表压扁；而两个按钮各占一半宽度，仍放得下「今天已请假」这五个字。上一版那句「· 点此恢复」也因此去掉——两半宽度里塞不下，改成「已请假」+ 实白底表示可点。

**改法上避开了两个坑**：切换外观不用反射式 `setBackgroundResource`（部分启动器上会让整次更新失败），而是同一格里叠两层 `TextView`，只切 `setViewVisibility`；旧的 `TOGGLE_TOMORROW` 广播 action 保留不动——已经放在桌面上的旧组件实例，`PendingIntent` 里还烧着它。

### v0.47.1（versionCode 88）— 修好「本周班表」小组件

**它从 v0.24.0 上线起就没成功加载过。**

桌面上的表现就是那句「载入窗口小部件时出现问题」。原因很具体：布局里用 `<View>` 做「今天」那一格的半透明高亮层，而 `RemoteViews` 只允许白名单里的控件——`android.view.View` 不在其中。启动器 inflate 到第七行就抛异常，整块组件直接放弃。

之所以拖了这么多版没发现：所有单测都在读 `computeModel()` 算出来的数据，没人真的把 `RemoteViews` inflate 过一次。数据全对，界面全废。

**改法**：高亮层从 `<View>` 换成 `FrameLayout`（同样能承载背景，且在允许列表里）。七格班表、今天高亮、底部「明天不上班」按钮现在都能正常显示。

**顺手把添加组件时的困惑也修了**：以前两个组件在列表里都叫「打工人闹钟」、都用同一个时钟图标，根本分不清哪个是哪个。现在分别叫「下一个闹钟」和「本周班表」，并各自用真实布局做预览（Android 12 起生效）。

**还加了一道防线**：新增 `WidgetRemoteViewsTest`，把两个组件的 `RemoteViews` 真的 inflate 成 View 树，逐格核对文案、高亮与按钮。以后谁再往小组件布局里塞一个白名单外的控件，单测当场就红。

### v0.45.0（versionCode 85）— 长按复制、后三次响铃

**① 长按一条闹钟：复制 / 删除。**

删一条原本要点开编辑框、再点删除，四步；而「照这条再来一个」更常见——以前只能新建一遍再把时间规则重填一遍。现在长按行弹两项菜单，复制会连规则一起带过来，名称加「副本」，默认开启。

**② 点倒计时，看接下来三次。**

倒计时那一行现在可点，弹出三行：明天 07:30 起床 / 后天 07:30 起床 / 10月26日 周一 07:30 起床。用的是纯规则计算，不去逐条探测系统登记状态——用户问的是「接下来会响什么」，不是「系统里登记了几条」。

**④ 设置页「按键设置」拆成两行。**

「音量键：稍后提醒 · 电源键：关闭」挤在一行约 200dp，右侧还有箭头，360dp 屏余量很小；字号一调大就折成「…电源 / 键：关闭」这种断在词中间的怪样子。现在两个键各占一行。

**顺手：**

- 桌面小组件复用首页刚算好的「下一个闹钟 / 提醒总数」，不再重复做一次跨进程探测；桌面没放小组件时一次模型都不算。
- 闹钟行的开关补了无障碍描述，TalkBack 读的是「07:30 起床 闹钟开关」，而不是光秃秃的「开关，已开启」。
- 闹钟列表写入改成同步落盘。这份 JSON 只有几百字节，而写完紧接着就要读（排程、重画列表），异步落地会让读回旧值、误判成「首次安装」而把预置闹钟塞回来。

### v0.44.0（versionCode 84）— 一键「今天不上班」，日历独立成页

**① 标一天假，从四步变成一步。**

原来的路径是：滚到日历卡 → 找到今天那个格子 → 点一下 → 在对话框里确认。而「今天临时有事、不想被闹钟吵」恰恰是最急、也最常发生的那一种操作——你正忙着，却要在一个月历里找今天。

现在今日状态卡底部有两个按钮（今天 / 明天）：上班日写「不上班」，休息日写「要加班」，点一下生效、再点一下撤销；生效后按钮变实白底、文案改成「已请假 / 已加班」。日历里同步显示，两边改的是同一份数据。

**② 排班日历独立成页。**

主界面内容原来约 1250dp，日历一张卡就占 460dp——改个闹钟时间得先滚过一整个月的格子。而日历的真实用法是「偶尔核对、临时标个请假」，不是每天必看。

现在主界面只留一行入口：**排班日历 › 今天上班 · 请假 1 天**。点进去是完整月历（班/休/假/补/节日、图例、请假加班清除都在），点灰字日期翻到那个月，右上角「今天」跳回当月。

**③ 顺手清掉一个隐患：读列表不再改数据。**

`Prefs.getAlarms()` 之前会在读的时候顺手把过期的一次性闹钟关掉并写盘。出发点是对的（三条消费路径自动一致），代价是一个叫 `get` 的方法有副作用：导出备份、生成新 id、小组件刷新这些纯查询也在悄悄写盘。

现在拆成两半：`getAlarms()` 纯读，`settleExpiredOnce()` 显式结算，`getAlarmsSettled()` 给「读完必须立刻用最新状态」的三条路径（列表渲染、排程、睡前提醒）。三处各钉了一条测试，防止哪条路径忘了结算又冒出「显示已开启、永远不会响」的闹钟。

**④ 日历格子高度按字号算。**

原来固定 46dp，是照默认字号量的。系统字体调到 2.0× 时，13sp 数字 + 9.5sp 标签装不下，两行会挤在一起甚至被裁掉。现在按 `Paint.FontMetrics` 量出真实行高再加内边距，字号多大都装得下；量不出来时回落到 46dp。

这一版没有新功能，全是「用起来别扭」的地方。攒着一起改，是因为它们都属于同一类问题：**同一个 App 里，两处做同一件事，做法却不一样。**

**① 主界面底部那三行小字，收进了一张卡片。**

「闹钟已开启 · 未来 90 天共 123 个提醒 / 下一个闹钟：10月21日 周三 07:30 起床 · 系统已登记 ✓ / 当前基准（大周周六）：2026-10-24 / 已内置 2026 年节假日安排……」——这些是核对用的信息，却常年占据主界面最底部近 100dp，而且「系统已登记 ✓」这种自检文案天天摆在眼前，像没做完的调试页。

现在它们收进「运行状态」卡，默认收起。收起时只有一行：**已开启 · 123 个提醒**。想看细节点开，四行都在。主界面少了一截，也没有信息被删掉。

主界面为了避开澎湃 OS 把框架选择器渲染成表盘拨轮，早就换成了自绘的「时 / 分」滚轮；引导页却一直还是 `TimePickerDialog`。同一个 App 里选时间出现两种完全不同的交互，而最花哨的那个偏偏在用户第一次打开时。

**④ 响铃页的大时钟不会再折成两行。**

76sp 是照着 360dp 屏算的。系统字体调到 1.5× 之后，「00:00」放不下，会折成「00:0」和「0」上下两行——全屏页最难看的一种坏法。现在加了单行 + 自动缩放：放得下还是 76sp，放不下按比例缩到 48sp。

- 「仅一次」的选项文案还写着「响完自动删」。上一版已经改成「只关不删」，说明文字没跟上——用户看到的第一句解释就是错的。

### v0.42.0（versionCode 82）— 一次性闹钟响过只关不删

**响完就从列表里消失，是我上一版想岔了。**

当时的理由是「响过即弃，才像一次性」。可实际用起来，一条闹钟响完就没了，用户会怀疑自己是不是根本没建成，或者建错了时间——尤其早上刚被叫醒、脑子还没转的时候。想照着这条再设一次，也找不到参照。

现在改成：**响过之后条目留在列表里，开关自动关闭，副标题写「已响过 · 10月21日 周三」**。一眼就能看出它为什么是关着的，而不是像「已停用」那样让人以为自己关过。

**顺手补了一个坑：** 关掉之后再打开它，日期还停在过去——那会是一条「显示已开启、永远不会响」的哑弹。现在打开时自动顺延到下一个同一时刻（今天没过点就是今天，过了就是明天），并弹一句「这个时间已经过了，已改到明天 · 10月22日」，跟新建时说的一样。

### v0.41.1（versionCode 81）— 一次性闹钟的三处漏洞

上一版刚加「仅一次」，这一版是把它自己捅的窟窿补上。三个都是我在写完之后回头查出来的，不是等它真出问题。

**① 请假当天，它被一起静音了。**

请假过滤写在排程的「天」那一层：那天请假，整天跳过，所有闹钟一起不响。这对「仅上班日」是对的——请假就是「今天不上班，别按作息吵我」。可一次性闹钟是另一回事：用户指着日历说「这天要叫我」，哪怕那天正好请了假（赶车、赶飞机、约了人），也该响。

现在请假豁免一次性闹钟。而请假过滤散在**排程、计数、下次响铃、自检**四个地方，任何一处漏掉都会出现「首页说会响、实际不响」——所以判断抽成了一个方法，四处共用。

**② 响完还赖在列表里到第二天零点。**

原来的过期判断只比日期，于是今天 6:30 响过之后，它还要在列表里躺到明天——你看着一条已经响完的闹钟，会怀疑它是不是还会再响一次。改成按**时刻**判断，响完即消失。

> 这条在 v0.42.0 又改了：「消失」换成「自动关闭、条目保留」——见下文。

**③ 写列表时没标记「已迁移」，写完可能被预置闹钟覆盖。**

这个最隐蔽：读列表时若发现「还没迁移过」，会预置一条「起床」和一条「午休」再返回。而写列表时没有顺手把「已迁移」置上，于是**先写后读**会被当成首次启动，刚写进去的整份列表被这两条预置的顶掉。真机上的触发条件是「装好后还没读过列表就写」——比如从备份恢复。

**顺带三处小的：**

- 编辑对话框外面套了 `ScrollView`。加了第四个模式与「哪一天」行之后，小屏上内容会超出对话框高度，而对话框本身不滚，底部的「删除 / 取消 / 保存」会被顶出屏幕——等于没有保存按钮。
- 「哪一天」的相对说法里去掉了「本周末」。五天后的周日不是「本周末」，与其判断周次，不如不给相对词：绝对日期本来就在后面写着。
- 响铃页的 inset 处理不再写死 `32dp`，改成读布局自己的内边距。原来那是两份独立的值，谁改了布局谁就会看到内容多一截，而且很难联想到那行代码。

### v0.41.0（versionCode 80）— 临时闹钟 + 提前提醒改成开关

**新增「仅一次」。** 原来的三种模式都挂在周休制度上：仅上班日、每天、仅休息日。它们回答的是「我平时的作息」，可有些闹钟根本不属于作息——赶车、赶飞机、明早临时开会、约了人。

为这一次去改整套制度不值得，而新建一条「每天」的闹钟，第二天就会在不需要的时候响。所以编辑对话框多了第四个选项：

| 模式 | 什么时候响 |
| --- | --- |
| 仅上班日 | 按周休制度自动排，节假日与调休都认 |
| 每天 | 每天 |
| 仅休息日 | 随制度：双休=周六日，单休=那一天 |
| **仅一次** | **只在选中的那一天响，响过自动关闭、条目留着** |

勾上「仅一次」，下面会多出一行「哪一天」，点开是未来七天的列表——**今天 / 明天 / 后天**打头，往后是「周五 · 10月24日」。临时闹钟本来就是近事，一个七天列表比日历更直接。

三处细节值得说：

- **它不看任何制度。** 那天是休息日、法定节假日、还是你请了假，都照响。这正是它存在的意义——「明早临时有事，早点起」不是「按制度排的班」。所以哪怕那天全公司放假，它也会叫醒你。
- **时间已过会自动顺延，并当面告诉你。** 上午九点建一条「今天 6:30」，它不会响，第二天还会被当成过期数据悄悄删掉——你等了一整天，什么都没发生。现在会顺延到明天的 6:30，并弹一句「这个时间已经过了，已改到明天 · 10月22日」。**没有静默处理**：改了你选的日期，就得说一声。
- **过期即清理。** 清理放在读取列表的唯一入口，排程、列表、睡前提醒三条路径自动都对——不会出现「昨天该响、之后再也不会响」的僵尸闹钟占着位置。

**响铃前提醒改成「标题 + 副标题 + 开关」。** 原来只有一行「响铃前提醒 …… 关闭」，想开得先点进去才知道里面有什么档位。现在：

| 状态 | 副标题 |
| --- | --- |
| 关 | 响铃前先发一条通知 |
| 开 | 提前 1 小时提醒（或你选的档位） |

整行点了就是开/关，**点副标题仍可调提前量**。关着的时候副标题说的是「这东西开着会怎样」，而不是复述一个「关闭」——后者等于把开关状态念一遍，看完还是不知道开了有什么用。

顺带修掉一个自己埋的坑：开关关掉会把值写成 0，再打开时读到的「上次的值」也是 0，于是回落默认 1 小时——注释里承诺的「关掉再打开还是原来的数」根本是空话。现在另存一个「上次选过的非零值」，关掉再打开回到 15 分钟就是 15 分钟。

**一处跟着变的语义：** JSON 里模式编号越界时，以前是「钳到最大」（那时最大是「仅休息日」，无伤大雅），现在最大是「仅一次」——钳过去会造出一个没有日期、永远不会响的闹钟。改成越界一律兜回「仅上班日」。

### v0.40.4（versionCode 79）— 响铃页铺满整屏，去掉上下白边

**不是刻意留的，是我漏了。** 锁屏响铃时屏幕上下各一条白边——顶上是状态栏，底下是导航条。

根因是「背景画在哪」和「谁负责那两条」不是一回事。紫色渐变画在内容区的 LinearLayout 上，而状态栏和导航条归窗口与系统管，它们取的是主题的颜色：主主题的 `statusBarColor` 是浅色，`windowBackground` 又是 Material3 的白——于是两条白边夹着一块紫屏。

**修法不是给那两条「填成紫色」。** 填色只能让它们变成纯色，而页面是 135° 渐变，顶和底的颜色跟中间不一样，硬填会在接缝处断成两截。正确做法是让内容画到系统栏底下：窗口背景直接给整屏渐变，系统栏设为透明透出它——**整屏只有一份渐变，根本不存在接缝**。

| | 之前 | 现在 |
| --- | --- | --- |
| 顶部一条 | 白（主题色） | 透出整屏渐变 |
| 底部一条 | 白（主题色） | 透出整屏渐变 |
| 系统栏图标 | 深色（紫底上看不清） | 浅色 |

内容则要按**真实 inset** 挪回来，不能写死 `paddingTop`——状态栏高度因机型而异，刘海、挖孔、灵动岛各不相同，写死必然在某些机型上被切。所以是读系统给的 inset，再叠加布局原有的 32dp。

顺带修了同一处的另一个毛病：`bg_hero` 带 **22dp 圆角**，那是给卡片用的（首页横幅、小组件），响铃页是整屏接管，没有「卡片」这层意思，留圆角只会让四角漏出底色。现在整屏版单独一份无圆角的渐变。

### v0.40.3（versionCode 78）— 修：稍后提醒的图标跑偏了

**v0.40.2 那个「图标 + 文字」的胶囊按钮，图标被钉在了胶囊最左边。** 真机上一眼就看得出来：文字在正中间，图标孤零零躺在左边角，中间隔着一大段空白。

原因是 `TextView` 的复合图标（`drawableStart`）在「宽度 match_parent + gravity=center」下**不参与居中定位**。探针量出来图标 bounds 是 `Rect(0, 0 - 18, 18)`——left 等于 0，就是贴着按钮左边。位置算错了，不是偏移了几像素。

改成 `LinearLayout` 显式排版：图标 `ImageView` 和文字 `TextView` 各自是子 view，由 `gravity=center` 统一居中。这样定位结果只取决于子 view 自身，不依赖 `TextView` 那套容易出问题的复合图标计算。

**顺带留了 4 条断言钉住它**：图标与文字间距 0~8dp、整组居中偏移 ≤4dp、图标不贴在左边缘（直接钉死老 bug）、按钮文字仍是稍后提醒文案。以后谁再把它改回 `TextView + drawableStart`，测试立刻红。

### v0.40.1（versionCode 76）— 响铃页不再说谎

**响铃页最下面那行一直写着「滑到底才会停 · 铃声会一直响」。** 上一版把响铃时长默认改成 10 分钟后，这行字就成了假的——界面说会一直响，实际 10 分钟就停了。

| --- | --- |

| 不限 | 滑到底才会停 · 铃声会一直响 |

### v0.40.0（versionCode 75）— 稍后提醒 / 提前提醒搬进引导页

**上一版把响铃前提醒默认打开了，紧接着的疑问是：有人嫌吵怎么办。** 最省事的做法是改回默认关闭——但那只是把问题藏起来：关着的时候，不知道有这功能的人永远不会知道，而「提前一小时知道明早还要响」恰恰是这类信息里最有用的那条（够决定今晚要不要早点睡，也够在响之前把它关掉）。

真正的分歧不是「该功能不该有」，而是「各人要多少」。既然是个人口味，就该让人当面选一次，而不是替他决定。所以引导页第 2 步在「响铃音量 / 渐响」下面多了两行：

| 新增行 | 默认回显 | 点开就是 |
| --- | --- | --- |
| 稍后提醒 | `5 分钟 × 3 次` | 间隔（3/5/10/15/30 分钟）+ 最多几次（1/2/3/5/不限） |
| 响铃前提醒 | `提前 1 小时` | 关闭 / 5 / 10 / 15 / 30 / 60 分钟 |

默认值一个没动，但它们第一次配闹钟时就摆在眼前——嫌吵当场关掉，比事后去设置页翻强。

**顺带交代「还有什么该进引导页」这个问题。** 我按三条标准筛：**默认开着**（关着的进了也是白进）、**第一次就会遇到**、**用户不主动找就发现不了**。按这个标准，剩下的都不该进：

- **睡前提醒**：默认关，而且依赖各人作息，逼人在引导里挑一个时间等于瞎填
- **铃声 / 震动**：默认铃声已经能响，属于「以后想换再换」的口味项
- **一周开始日 / 提醒范围**：有合理默认，绝大多数人一辈子不会动
- **节假日数据、导入导出**：不是第一次启动该做的事

引导页每加一行都在消耗耐心，宁可少——它现在三页，第 2 步四行，是「看完就能用」的上限附近。

**一份代码两处用。** 这两个对话框的「档位 ↔ 存值」映射原先只写在设置页里，现在抽成 `PrefDialogs` 给两边共用，不会出现改了设置页忘了改引导页的漂移。

**顺便把更新日志本身精简了。** 之前的条目动辄七八条、每条三四行，三十几版堆在一起像论文——而它的用途只是「升级后扫一眼这版改了什么」。现在收紧成**每条一行、每版最多三四条**，只留「改了什么」，把推导过程留在这份说明里。想看完整取舍的，看上面就够。

### v0.39.1（versionCode 74）— 三处默认值改得更像默认值

**默认值是产品态度的体现：它决定了「什么都不设置的人」会拿到什么。** 之前三处的默认值都偏保守——响铃不限时长、稍后提醒只能一次、响铃前提醒干脆关着。保守看起来安全，实际是把三个最有用的行为默认关掉了。

| 设置 | 原默认 | 新默认 | 理由 |
| --- | --- | --- | --- |
| 响铃时长 | 不限（一直响） | **10 分钟** | 没人管的时候不该一直响。响铃页改成滑动停止后，睡过头或滑不动时「一直响」没有下限 |
| 稍后提醒次数 | 1 次 | **3 次** | 只给一次的话，按掉之后想再眯五分钟就没机会了；而「还要不要再睡」恰恰是刚响铃时最做不到的决定 |
| 响铃前提醒 | 关闭 | **1 小时** | 提前一小时知道「还要响」是有用的信息——够决定今晚要不要早点睡，也够在响之前把它关掉 |

**只影响新安装。** 已经改过这些设置的用户不受影响——不会因为升级就把你原来的选择覆盖掉。三者在设置页都能一行改回。

**一个副作用要说清**（文档「响铃前提醒」一节原本就写着，现在它从"你开了才会遇到"变成默认就会遇到）：响铃前提醒开着时，每个响铃实例会多占一个系统闹钟名额，主闹钟的排程上限因此从 400 天减到 200 天。系统闹钟槽位由主闹钟和提前通知共用一份预算，不能因为多了一条提醒就把总数顶到 ROM 的 500 硬限——那是早先闪退的根因。代价由滚动补排兜住：每天响铃后都会重排，窗口不断前移，所以「能排多少天」不等于「多少天后会漏响」。

### v0.39.0（versionCode 73）— 单休收成一项，休哪天单独选

**引导页第一页原来有四张卡：大小周 / 双休 / 单休·周日休 / 单休·周六休。** 后两张其实是同一个制度的两个取值——「单休」是制度，「休周六还是休周日」是它的一个参数。并排放着，用户得先读完两行小字才知道该点哪个；而且看到两个平级选项，第一反应往往是「这两个是不是还有别的区别」。

现在压成三张卡。选中「单休」后下面多出一行**休哪天：休周日 / 休周六**，卡片副标题同步变成「周日休 · 周六上班」，不用回头猜自己选的是哪种。

几个取向：

- **第一次点单休默认「休周日」**——国内绝大多数单休如此。真休周六的人点一下旁边的「休周六」就换过来了，比让每个人从两个必选项里挑一个更轻。
- **已经是单休的用户重看引导时沿用原来那天**。若写死成「休周日」，老用户只是想改个闹钟时间，排班却被悄悄改掉——「顺手改了不该改的」比多一步操作严重得多。
- **设置页仍保留完整四项**（双休 / 单休·周日休 / 单休·周六休 / 大小周）。那里是直接改一项设置，再套一层分级反而多一次点击；引导页分级是为了降低第一次选择的负担，两处场景不同，不必强行统一。

### v0.38.0（versionCode 72）— 响铃页改成滑动停止

**闹钟响时人是半睡半醒的，这时候一个占满屏宽的「停止响铃」按钮就是个陷阱**：手一碰到就关了，人还没醒。滑动要求一段**有方向的位移**才能触发，误触概率低一个量级——这也是正经闹钟都用滑动的原因。

几个细节是反复权衡过的：

- **滑到九成就算数**，不要求真的顶到最右端。手指滑到末端常常差一点，要求 100% 会让人反复重试，那就不叫防误触，叫为难人。
- **没滑到就弹回原点**，而不是停在半路。半路的进度看着像「已经做了一半」，会诱导人再滑一点，也可能被当成界面卡住了。
- **只有按住滑块才能拖**。按轨道空白处也能拖的话，整块区域又变回一个大按钮，等于白改。
- **「稍后提醒」仍然是点按**。半睡半醒想多睡 5 分钟，不该要求精确操作——防误触只该用在「彻底关掉」这个不可逆的动作上。
- **无障碍下点一下也能停**。TalkBack 用户执行不了滑动手势，滑块对他们就是个永远关不掉的闹钟。

滑块是纯自绘的（Canvas），没引第三方库。

### v0.37.1（versionCode 71）— 修：改完闹钟，列表和倒计时差 30 分钟

**改完闹钟时间回到主界面，列表和顶部倒计时显示的不是一个时间。** 实测：把起床从 07:30 改成 07:00，列表还写 07:30，顶部却说「下次 07:00」——同一个闹钟，两个时间。

根因是两处读的不是同一份数据。闹钟列表渲染用的是 `onCreate` 时读进来的那份快照，之后无论刷新多少次都拿它；而倒计时走 `ScheduleManager.nextRing`，每次都重新读设置。于是**改一次就分叉一次**：第一次改动后列表是旧的、倒计时是新的，再改一次差距继续累积。

这不只是显示难看：列表上的闹钟开关、标签、启用状态同样来自那份快照，改完返回看到的其实都是改之前的样子。

修法是把数据源统一。抽出 `reloadAlarms()`，每次全局刷新都重读；倒计时不再自己去读一遍设置，而是直接吃刚读到的那份列表。两边从此不可能对不上。

### v0.37.0（versionCode 70）— 音量与渐响搬进引导页

**「会不会响」是这个 App 唯一需要证明的事，但以前要等到第二天早上才知道。** 权限清单只是文字上的「已开启」，用户点完四项，心里还是没底：真响起来是什么样？横幅弹不弹？

### v0.35.0（versionCode 68）— 引导页改成「顺手配完」

**引导页原来在念说明书。** 三页讲完「周休制度是什么 / 闹钟怎么响 / 记得开权限」，用户点完「开始使用」进主界面，还得自己再走一遍：选制度、加闹钟、翻设置开权限。同一件事讲两遍，第一遍还全是字。

### v0.34.0（versionCode 64）— 被折叠时，一键改回来

**折叠卡片生效了，但澎湃把它收进了「更多通知」。** 这个不是布局的问题，是「通知过滤」——小米自己的文档写得很清楚：评分模型按**通知文本、这台设备的历史点击率、用户属性**打分，分数低于阈值就判为不重要、收进二级页。里面还提到一条：新装应用的前 3 条通知默认重要（首 x 条保护），之后就看点击率了。

**没有 API 能强制某条通知为「重要」**，这一点我不绕弯子：翻遍 `Notification` / `NotificationChannel`，没有一个字段对应「重要 / 不重要」。能改的只有系统侧这两处：

- 左滑那条通知 →「设为重要」，之后这个应用的通知长期保持重要，不会再被折叠
- 或者 设置 → 通知和状态栏 → 关掉「通知过滤」（全局开关，影响所有应用）

**为什么这条值得认真对待**：官方文档说「设为重要」是**设备级、长期生效**的——设一次，以后每次响铃前提醒都直接躺在通知栏里，不用再点进「更多通知」。这比在 App 里绕任何弯子都管用。

顺带说一句：就算被折叠，锁屏上该弹的提醒照弹（`PreNoticeActivity`），功能不会丢，只是那条常驻通知要多点一次才看得到。

### v0.33.0（versionCode 63）— 锁屏卡片上也能关闹钟了

**前两版都在解决同一个问题，但都只解决了一半。** 你截图里那个位置是**锁屏卡片**，不是下拉后的通知栏。锁屏只渲染通知的**折叠态**，而 `addAction` 的按钮只存在于**展开态**——所以不管是补图标（v0.31.3）还是画 heads-up（v0.32.0），锁屏卡片上都不会出现按钮。这是我之前没看清楚的地方。

**真正的解法是把按钮画进折叠态布局**。`setCustomContentView` 换掉系统模板，折叠态就由 App 自己的 RemoteViews 说了算，锁屏卡片和「下拉但没展开」的卡片都走这一套。现在的卡片是：左侧圆形底的闹钟图标，中间「午休 即将响铃」+「1 小时后 · 15:42 响铃」，右侧「关闭闹钟」药丸。点药丸只关这一次，点其余位置仍然进详情页。

**顺带改掉那句啰嗦的正文**：原来写「1 小时后（15:42）响铃 · 点此查看」，现在写「1 小时后 · 15:42 响铃」。折叠卡片只有一行的位置，说清楚几点响比说「点这里」有用。

自绘布局一共三套，各管一个形态，互不复用：折叠卡片（`notif_content`）、横幅（`notif_heads_up`）、以及下拉展开后系统模板里的 action 按钮。夜间模式三套都另配文字色和底色。

### v0.31.1（versionCode 58）— 解锁时不再抢屏

**一条规则管住三处**：手机解锁使用中，只弹一条横幅通知；锁屏或息屏，才弹整屏界面。之前正式响铃和响铃前提醒都是「横幅 + 整屏」一起来，用户正看着屏幕时整屏盖上来，纯属打扰。

判断依据是 `ScreenLock.shouldPopup()`：屏幕不处于交互状态（息屏）**或** keyguard 处于锁定状态，就弹窗；否则只发通知。把「息屏」单独算一条，是因为没有锁屏密码的设备息屏时 keyguard 并不算 locked，只判锁定状态会漏掉「放在桌上息屏」这个最常见的场景。

**测试响铃单独处理**：它是用户主动点的按钮，页面本来就该打开，所以仍直接打开响铃页；但前台服务那条通知改用低优先级渠道（`test_channel_v1`），不再叠一条横幅。之前「测试」是横幅和页面同时出现，最明显的就是这一处。

**修**：响铃前提醒在解锁时横幅和整屏弹窗同时出现。

测试 **236 个，0 失败**（新增 7 个：解锁 / 锁屏 / 息屏三种状态下的判断，以及正式响铃、响铃前提醒在解锁与锁屏时是否真的去拉界面）。

### v0.23.1（versionCode 45）— 稳定性与性能

**修掉的 Bug**

- **跨天后旧闹钟取消不掉（影响最大）**：闹钟的内部编号原先按「距今天几天」算，跨天后再取消时算出的编号已经变了，导致旧实例留在系统里——可能同一天响两次，还会挤占系统的闹钟名额。改为按绝对日期编号，并在升级后自动清理一次旧编号残留。
- **两个闹钟同时到点会叠着响**：比如起床 7:30 和另一个 7:30 的闹钟，第二路铃声会覆盖第一路的引用，旧铃声既停不掉也释放不了。现在开始新响铃前先收尾上一路。
- **按音量键可以绕过「稍后提醒」次数上限**：按钮变灰后，把音量键设成「稍后提醒」的人仍能无限续睡。已与通知栏、界面按钮统一判断。
- **关掉总开关后「稍后提醒」还会响**：点了小睡再关开关，几分钟后照样响。现在关开关会连待触发的小睡一起清掉。
- **转屏会让闹钟静音**：闹钟页旋转重建时旧代码无条件停掉铃声。现在只在真正退出时停。
- **改时区 / 手动改系统时间后闹钟时刻偏了**：新增监听，时区或系统时间变化后自动重排。
- **节假日数据源返回垃圾内容会清空已有数据**：结构合法但没有版本号的 JSON（如 `{"error":"not found"}`）以前会被当成空数据合入。现在直接拒绝，并保留原有数据。
- **23:58 响铃 + 自动停止跨零点时残留一条广播**：取消时用错了日期，现在按实际注册日期取消。
- **通知栏「稍后提醒」跨零点记错日期**：补上了缺失的日期参数。
- **「请假标记：37 天」看着像出错**：统计只算今天及以后，过去的日子不再计入。
- **闹钟页返回键提示写死「5 分钟后再响」**：改为跟随实际设置。

**性能优化**

- **主界面刷新不再卡**：「下一个闹钟」原先要把未来 90~365 天的每个候选都向系统查一次（约 1000 次跨进程调用），现在按时间排序、查到第一个就停。
- **改设置时少拷贝上千次集合**：请假 / 加班日期改为每次重排只读一遍（原来在「闹钟数 × 天数」的双层循环里逐日读取）。
- **响铃瞬间不再阻塞**：响铃后的重排要注册上百个系统闹钟，已挪到后台线程，界面和服务立即起来；开机广播同理，避免超时。
- **重复代码合并**：`countScheduled` 与 `pendingAlarmCount` 原本是两份一模一样的循环，已合并；主界面每次刷新少跑一遍全量统计。
- **桌面小组件加 30 分钟兜底刷新**：长期不打开 App 时，小组件不会一直停在上次写入的「下一个闹钟」上。
