# 流程规范 · 打工人闹钟

> 写于 2026-10-22 14:30。起因是用户问「我们现在的开发流程合理吗」，
> 诊断出三个短板：**验证全靠人肉、视觉决策在事后、文档在膨胀**。
> 这份文件把改进固化成规则，每次动手前扫一眼。
>
> 骨架没问题，不用推倒：小步提交、每版有测试、每版有日志、跨会话有交接——这四条继续。

---

## 一、布局改动前先出线框预览（最重要的一条）

**规则：凡是动布局，先画线框给用户看，他点头再写代码。**

原因：Robolectric 不渲染真实像素，布局对不对只有真机知道。上一轮的代价是
v1.46.2 → v1.46.3 → v1.46.4 三次往返，每次用户都要下载、安装、试用，然后说「不对」。

**怎么做**

1. 画一张 HTML 线框图，**按真实 dp 比例**（本机 354×786dp，扣掉状态栏与手势区，可见约 700dp）
2. 标注：每块的高度、累计高度、**第一屏分界线在哪**
3. 要对比就左右并排（改前 / 改后），并写出各自的屏数
4. 存成 `docs/预览-<主题>.html`，用 `present_files` 打开给用户看

**高度从哪来**：`布局现状清单.md` 里有实测值。没有实测值就现算——
`paddingTop + paddingBottom + 内容高 + 卡头`，**别只算内容**（「标题并卡」那次就栽在这，
估省 188dp，实际净省 44dp）。

**线框不必好看**，灰块 + 文字 + 数字就够。它的作用是把「好不好看」之外的问题
（够不够高、顺序对不对、第一屏装得下什么）在动手前定下来。

## 二、一个功能想清楚整件事的样子再动手

**规则：动手前先用一句话说清「做完之后长什么样」，说不清就别开工。**

反例：v1.46.2 / v1.46.3 / v1.46.4 三刀，本质是同一件事（首页瘦身）的三次尝试，
却占掉三个版本号，看起来像三次功能升级。如果第一刀之前就问「首页最终该是什么顺序、
第一屏该装下什么」，一次就能到位。

**开工前的三个自问**：

1. 做完之后，用户看到的第一屏是什么？第二屏是什么？
2. 这件事有没有可能一次做完？如果要分步，每步之间用户能不能用？
3. 会不会引入新的「需要解释自己」的机制？（见第五条）

---

## 三、一版一主题，版本号跟着改动性质走

**规则：一个版本只做一件事；同一件事分几次做完，只涨修订号。**

细则见 `交接-给下一个会话.md` 第 4 节「版本号规则」。核心三条：

| 改动性质 | versionName |
| --- | --- |
| 删功能 / 改数据格式 / 重写 | 主版本 +1 |
| 加功能 / 改交互 | 次版本 +1 |
| 修 bug / 调文案 / 调布局 | 修订 +1 |

**发版节奏**：不要每个小改动都出包。攒到「用户能感知到一件事变了」再发。
用户只有一个，他每装一次包都要动手，这个成本比我们出包的成本高得多。

## 四、文档各管一摊，同一事实只写一处

**规则：一个事实只能有一个权威位置，其他地方引用，不复制。**

上一轮的教训：交接文档里「现状」同时出现在三处，结果一处改成 v1.46.4，另一处还写着 v1.42.0。

| 文件 | 唯一职责 | 不该写什么 |
| --- | --- | --- |
| `交接-给下一个会话.md` | 当前状态、环境、待办、坑 | 逐版详细记录 |
| `历史-版本记录.md` | v1.34.0 起的逐版要点 | 当前状态 |
| `流程规范.md`（本文） | 怎么干活 | 具体版本的状态 |
| `布局现状清单.md` | dp 实测值、布局改动记录 | 待办 |
| `优化与新功能建议.md` | 待办池、已否决项 | 已完成的事 |
| `打工人闹钟-使用说明.md` | 面向用户的操作说明 | 更新日志 |
| `更新日志.md` | 面向用户的版本历史 | 操作说明 |

**体积红线**：交接文档 **15 KB 以内**，超了就说明又在往里塞历史。
使用说明 **30 KB 以内**，超了说明在往里塞日志。

**写文档的判据**：这条信息如果不写，下一个会话会做错事吗？会 → 写；不会 → 别写。

## 五、警惕「需要解释自己」的机制

**规则：一个功能如果需要在三处以上补一句说明，它本身就不该存在。**

这是删「闹钟总开关」时总结出来的。它需要五处解释：今日卡副标题、倒计时留空、
桌面小组件「尚未开启」、睡前提醒「总开关还没打开」、编辑弹窗「先打开才会响」。

**检查方法**：加一个开关 / 模式 / 状态位之前，先数一数「哪些地方要跟着判断它」。
超过三处，就该重新设计，而不是加更多提示。

## 六、测试守行为，不守文案

**规则：测试断言的是「点了 X 会 Y」，不是「标题写着 Z」。**

| 值得写 | 不值得写 |
| --- | --- |
| 关掉最后一条闹钟后，`cancelAllIncludingTransient` 被调用 | `assertEquals("尚未开启", m.title)` |
| 日历排在闹钟卡之后（顺序） | 某个 TextView 的 `textSize` 是 14sp |
| 布局里不该再有 `switch_alarm` 这个 id | 按钮文案是「添加闹钟」还是「+ 添加」 |
| 每个颜色在 `values-night` 有同名（防静默回落） | — |

**判据**：如果这条测试红了，是「代码错了」还是「我改了文案」？
后者占多数，就说明这条测试在收税，不是在守门。

已知的技术债：444 条里还有 66 处断言（整段比对 29 + `contains` 37）写着界面文案，等 1.47.0 清理。

## 七、每次收工前

1. 测试全绿（读 XML 数，别看 Gradle 输出）
2. 文档同步：交接文档的「现状」表、使用说明头部版本号
3. APK 复制到 `/workspace`，`present_files` 挂出
4. `git commit`，message 写清「改了什么 + 为什么」

---

## 八、什么时候该借外部视角（专家 / 子代理）

**结论（2026-10-22 定）：测试迭代期不接 WorkBuddy 专家。**

先把概念分清，避免每次重新讨论：

| 机制 | 本质 | 给的是 |
| --- | --- | --- |
| Skill | 流程 + 脚本 | **能力**：能做什么 |
| 专家 | 人设 + 方法论 + 工具链 | **视角**：用什么标准判断 |
| 子代理 | 独立上下文 + 同样工具 | **第二双眼睛**：能读能跑，成本低 |

专家**不增加能力**，只切换判断标准。接进来不会多出任何工具。

**为什么不接，三条理由：**

1. **瓶颈在别处**。这个项目最贵的一环是真机验证（见「附」第 1 条），专家碰不到真机。
2. **换专家 = 丢上下文**。召唤专家要开新对话，v1.46.4 / 440 条测试 / 1105dp / 折叠方案
   684dp / 5 个待验证点这一整套得重新交代。专家靠完整背景才起作用（BRC 框架），
   而本项目每天都在同一套上下文里推进，重述成本高于收益。
3. **专家适合「从 0 到 1 的产出物」，不适合「持续迭代的代码库」**。前者交代一遍背景就交付，
   后者要记住昨天改了什么、为什么。

**三个触发点，到了再借：**

| 时机 | 借什么 | 为什么那时值得 |
| --- | --- | --- |
| 发布期 | 文案 / 产品类专家 | 商店介绍、隐私政策、用户手册——纯产出物 |
| A11 UI 美化 | UI/UX 设计类 | 审美判断需要外部标准，工程视角给不了 |
| 架构重写 | 架构师 | 迁 Kotlin、拆模块这类一次性决策 |

**「审代码」这个需求，用子代理，不用专家**：能读全仓库、能跑测试、返回结构化意见，
不换会话、不丢上下文、成本低一个数量级。

**判据**：想借外部视角前先问一句——我要的是「多一种判断标准」，还是「多一双能跑代码的手」？
前者找专家，后者找子代理。都不是，就别接。

## 附：这套流程解决不了什么

诚实说清楚边界：

- **真机行为验证不了**。AlarmManager 到点是否真响、通知长什么样、厂商 ROM 会不会杀后台，
  这些只有用户装机才知道。所以试用期的 5 个验证点必须问，不能跳。
- **视觉审美判断不了**。线框能定结构和高度，定不了「好不好看」。A11 UI 美化那一轮
  仍然要用户看实物。
- **用户只有一个**。「这个功能有没有用」这类判断没有样本，只能靠推理和试。
  所以宁可先做小的、可撤的，也别一次上大的。
