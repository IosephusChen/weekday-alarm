# 流程规范 · 打工人闹钟

> 写于 2026-10-22 14:30。起因是用户问「我们现在的开发流程合理吗」，
> 诊断出三个短板：**验证全靠人肉、视觉决策在事后、文档在膨胀**。
> 这份文件把改进固化成规则，每次动手前扫一眼。
>
> 骨架没问题，不用推倒：小步提交、每版有测试、每版有日志、跨会话有交接——这四条继续。

---

## 〇、新想法先讨论，点头再动手（2026-10-23）

用户提出新想法 / 新需求时，**先不动代码**。先回一段：

1. **我理解的问题**——一句话复述，确认没跑偏；
2. **两三个做法**——各自要改哪里、有什么副作用、大概多大；
3. **我倾向哪个、为什么**；
4. **哪些只能真机验**。

等到明确一句「就这么做」再开工。

**为什么加这条**：这一天里出现过好几次「先做完再解释」，其中几轮用户的想法
本来有更简单的解法——「电池优化既然没用，还留着干嘛」，我上一版只是把它降级成
「可选」，是半吊子；用户一问，才改成直接删。**做出来再改，比先说清楚再做贵得多。**

**例外**（不必先问，直接做）：错别字、文档同步、补测试、用户已经明确说「就这么做」的收尾。

**也别走另一个极端**：一句话能说清的改动（改个默认值、删一行文案），
用两三行给结论 + 一句「我这就改」即可，不用摆出方案对比。

### 「去看看有没有别的 bug」是哪种授权（2026-10-30 补）

用户说「花点时间看看代码里还有没有其他 bug」时，授权的是**审查**，不是「随便改」。
边界按改动性质分：

| 改动性质 | 要不要再问 |
|---|---|
| 清理会崩的写法（未保护的 `release()`、裸 `catch` 里丢了资源） | 不用问，直接改 |
| 修的 bug 有明确「本来应该是这样」的答案，且不新增行为 | 不用问，但要在报告里逐条说清改了什么 |
| 会改变用户能感知的行为（显示什么、响不响、什么时候响） | 先给方案 |
| 新功能、新设置项、布局调整 | 先给方案，走第一 / 第二节 |

判断标准只有一句：**用户明早醒来，需不需要重新理解这个 App 怎么用。**
需要就是行为改动，先问；不需要就是内部修复，可以直接做。

## 一、布局改动前先出线框预览（最重要的一条）

**规则：凡是动布局，先画线框给用户看，他点头再写代码。**

原因：布局对不对，靠猜不行。上一轮的代价是 v0.56.1 → v0.56.2 → v0.56.3 三次往返，
每次用户都要下载、安装、试用，然后说「不对」。

> 2026-10-29 修正：原文写「Robolectric 不渲染真实像素」。**不准确**——默认的 LEGACY
> 图形模式下 Canvas 是空实现（画出来是全透明），但 `@GraphicsMode(NATIVE)` 能渲染真像素，
> v0.89.9 用它一次定稿通知卡片。所以线框和真像素渲染分工不同：
> **线框定结构（够不够高、顺序对不对），真像素定观感。** 见第十一条。


**怎么做**

1. 画一张 HTML 线框图，**按真实 dp 比例**（本机 354×786dp，扣掉状态栏与手势区，可见约 700dp）
2. 标注：每块的高度、累计高度、**第一屏分界线在哪**
3. 要对比就左右并排（改前 / 改后），并写出各自的屏数
4. 存成 `docs/预览-<主题>.html`，用 `present_files` 打开给用户看

**高度从哪来**：`布局现状清单.md` 里有实测值。没有实测值就现算——
`paddingTop + paddingBottom + 内容高 + 卡头`，**别只算内容**（「标题并卡」那次就栽在这，
估省 188dp，实际净省 44dp）。

**线框不必好看**，灰块 + 文字 + 数字就够。它的作用是把「好不好看」之外的问题
（够不够高、顺序对不对、第一屏装得下什么）在动手前定下来。

## 二、一个功能想清楚整件事的样子再动手

**规则：动手前先用一句话说清「做完之后长什么样」，说不清就别开工。**

反例：v0.56.1 / v0.56.2 / v0.56.3 三刀，本质是同一件事（首页瘦身）的三次尝试，
却占掉三个版本号，看起来像三次功能升级。如果第一刀之前就问「首页最终该是什么顺序、
第一屏该装下什么」，一次就能到位。

**开工前的三个自问**：

1. 做完之后，用户看到的第一屏是什么？第二屏是什么？
2. 这件事有没有可能一次做完？如果要分步，每步之间用户能不能用？
3. 会不会引入新的「需要解释自己」的机制？（见第五条）

## 三、一版一主题，版本号跟着改动性质走

**规则：一个版本只做一件事；同一件事分几次做完，只涨修订号。**

细则见 `交接-给下一个会话.md` 第 4 节「版本号规则」。核心三条：

| 改动性质 | versionName |
| --- | --- |
| 删功能 / 改数据格式 / 重写 | 主版本 +1 |
| 加功能 / 改交互 | 次版本 +1 |
| 修 bug / 调文案 / 调布局 | 修订 +1 |

**发版节奏**：不要每个小改动都出包。攒到「用户能感知到一件事变了」再发。
用户只有一个，他每装一次包都要动手，这个成本比我们出包的成本高得多。

**出包后必做（v0.75.2 加，R8 开启后）**：`assembleRelease` 会把
`app/build/outputs/mapping/release/mapping.txt` **覆盖掉**——那是把混淆后的崩溃栈还原成
可读代码的唯一钥匙。每出一版，立刻把它复制一份按版本号存档：

```bash
cp app/build/outputs/mapping/release/mapping.txt /workspace/mapping-vX.Y.Z.txt
```

（v0.75.1 的 mapping 已被 v0.75.2 的构建覆盖，找不回来了——该版没离开过测试机、
无线上用户，实际影响为零。v0.75.2 起按版本号存档。）

**release 包崩溃了怎么读栈（retrace）**：mapping 只是原料，还原用 SDK 自带的 `retrace`
（2026-10-25 用 v0.75.2 的 mapping 实跑验证过）：

```bash
/opt/android-sdk/cmdline-tools/latest/bin/retrace /workspace/mapping-vX.Y.Z.txt 崩溃栈.txt
```

把报错日志里 `at ...` 那几行存成文件喂给它即可。实测效果（v0.75.2 mapping）：

```
at m1.w0.n(m1.w0.java:42)        → at io.github.iosephuschen.weekdayalarm.HolidayUpdater.fetchYear(HolidayUpdater.java:156)
at m1.a.a(m1.a.java:13)          → at io.github.iosephuschen.weekdayalarm.Alarm.appliesTo(Alarm.java:259)
at io.github.iosephuschen.weekdayalarm.AlarmActivity.onCreate(...)  → 本来就没混淆的帧原样透过
```

注意：**必须用崩溃那个版本的 mapping**（版本对不上行号会错位）；类被 R8 合并时，
还原显示的是合并后的宿主类（上面 `WeekWidgetRender` 的字段就挂在 `HolidayUpdater` 名下），
这是正常现象不是 bug。

## 四、文档各管一摊，同一事实只写一处

**规则：一个事实只能有一个权威位置，其他地方引用，不复制。**

上一轮的教训：交接文档里「现状」同时出现在三处，结果一处改成 v0.56.3，另一处还写着 v0.54.2。

| 文件 | 唯一职责 | 不该写什么 |
| --- | --- | --- |
| `交接-给下一个会话.md` | 当前状态、开工步骤、待办、坑 | 逐版记录、环境安装细节 |
| `恢复说明.md` | 环境、安装、恢复、签名 | 进度、待办 |
| `历史-版本记录.md` | v0.48.1 起的逐版要点 | 当前状态 |
| `流程规范.md`（本文） | 怎么干活 | 具体版本的状态 |
| `布局现状清单.md` | dp 实测值、布局改动记录 | 待办 |
| `优化与新功能建议.md` | 待办池、已否决项 | 已完成的事 |
| `打工人闹钟-使用说明.md` | 面向用户的操作说明 | 更新日志 |
| `更新日志.md` | 面向用户的版本历史 | 操作说明 |

**结构上限**（2026-10-22 19:25 取代原来的「交接 15 KB / 说明 30 KB 红线」）：

- **交接文档只放四类**：现状、开工步骤、活的待办、踩过的坑。
  具体命令（SDK 装法、`init.gradle`、签名指纹）只在 `恢复说明.md` 写一遍，这里给指针。
- **坑表每条一行，最多 12 条**；超了就把最老的 3 条移进 `历史-版本记录.md`，交接里只留还在咬人的。
- **待办只留没做完的**；做完的移到历史。
- **使用说明只写「怎么用」**，版本历史放 `更新日志.md`。

不按字节数卡：中文一个字 3 字节，数字节只会逼人删标点、并句子——改完看起来合规、读起来更差。
而且它会量错东西：红线触发时，真实原因可能是「同一段命令写了两遍」，也可能是「真的塞了历史」，
字节数分不出来。上一轮 15.35 KB 里最大的一块是环境步骤，不是历史。

**写文档的判据**：这条信息如果不写，下一个会话会做错事吗？会 → 写；不会 → 别写。

## 五、警惕「需要解释自己」的机制

**规则：一个功能如果需要在三处以上补一句说明，它本身就不该存在。**

这是删「闹钟总开关」时总结出来的。它需要五处解释：今日卡副标题、倒计时留空、
桌面小组件「尚未开启」、睡前提醒「总开关还没打开」、编辑弹窗「先打开才会响」。

**检查方法**：加一个开关 / 模式 / 状态位之前，先数一数「哪些地方要跟着判断它」。
超过三处，就该重新设计，而不是加更多提示。

## 六、测试守行为，不守文案

**规则：测试断言的是「点了 X 会 Y」，不是「标题写着 Z」。**

| 值得写 | 不值得写 |
| --- | --- |
| 关掉最后一条闹钟后，`cancelAllIncludingTransient` 被调用 | `assertEquals("尚未开启", m.title)` |
| 日历排在闹钟卡之后（顺序） | 某个 TextView 的 `textSize` 是 14sp |
| 布局里不该再有 `switch_alarm` 这个 id | 按钮文案是「添加闹钟」还是「+ 添加」 |
| 每个颜色在 `values-night` 有同名（防静默回落） | — |

**判据**：如果这条测试红了，是「代码错了」还是「我改了文案」？
后者占多数，就说明这条测试在收税，不是在守门。

「文案断言」要分两半看：模型输出的文案（`label` / `title` / `describe`，27 处）**就是产品输出，该测**；
UI 层的 `getText()` 断言（23 处）多是格式契约（表头、占位符），保留。
此前记的「66 处」把 `contains` 也算进去了——**统计口径写错比没统计更糟**，会让人去做无谓的重构。

## 七、每次收工前

发版这件事有 `tools/release.sh` 托底（文档一致性、全量测试、lint、出包、回填包信息），
下面这些是它做不了、必须人来的部分：

1. **测试全绿**，且读 XML 的条数而不是 Gradle 的终端输出——脚本已经这么做，改了测试仍要自己先跑一遍。
2. **文档同步**：`release.sh --check` 会逐条报（Changelog / 更新日志 / 使用说明三处 /
   交接现状表 / README 候选版号，共七处）。报出来的 FAIL 一条对一处，别跳过。
3. **APK 交付**：复制到 `/workspace` → `present_files` → 推给用户，三件都要做。
   只 `present_files` 不推，用户手机上不会出现；只推不 `present_files`，这次会话里找不到。
4. **`git commit`**，message 写清「改了什么 + 为什么」，坑和取舍一并写进去——
   半年后回来查的是这条 message，不是代码。
5. **推送**：`git push` 不通时走 `tools/push_via_api.py`。注意**标签不会自动跟着走**，
   要显式 `--tag vX.Y.Z`；这条 0.91.3 踩过，差点只推了分支。
6. **Release**：`tools/publish_release.py --mapping`。幂等，可重跑；同名资产要换加 `--force`。
7. **三方核对再报完成**：远端 HEAD、tag 指向的提交、Release 的资产列表。
   只看到「完成」两个字就回话，是这套流程里最容易翻车的地方。

## 八、什么时候该借外部视角（专家 / 子代理）

**结论（2026-10-22 定）：测试迭代期不接 WorkBuddy 专家。**

先把概念分清，避免每次重新讨论：

| 机制 | 本质 | 给的是 |
| --- | --- | --- |
| Skill | 流程 + 脚本 | **能力**：能做什么 |
| 专家 | 人设 + 方法论 + 工具链 | **视角**：用什么标准判断 |
| 子代理 | 独立上下文 + 同样工具 | **第二双眼睛**：能读能跑，成本低 |

专家**不增加能力**，只切换判断标准。接进来不会多出任何工具。

**为什么不接，三条理由：**

1. **瓶颈在别处**。这个项目最贵的一环是真机验证（见「附」第 1 条），专家碰不到真机。
2. **换专家 = 丢上下文**。召唤专家要开新对话，v0.56.3 / 440 条测试 / 1105dp / 折叠方案
   684dp / 5 个待验证点这一整套得重新交代。专家靠完整背景才起作用（BRC 框架），
   而本项目每天都在同一套上下文里推进，重述成本高于收益。
3. **专家适合「从 0 到 1 的产出物」，不适合「持续迭代的代码库」**。前者交代一遍背景就交付，
   后者要记住昨天改了什么、为什么。

**三个触发点，到了再借：**

| 时机 | 借什么 | 为什么那时值得 |
| --- | --- | --- |
| 发布期 | 文案 / 产品类专家 | 商店介绍、隐私政策、用户手册——纯产出物 |
| A11 UI 美化 | UI/UX 设计类 | 审美判断需要外部标准，工程视角给不了 |
| 架构重写 | 架构师 | 迁 Kotlin、拆模块这类一次性决策 |

**「审代码」这个需求，用子代理，不用专家**：能读全仓库、能跑测试、返回结构化意见，
不换会话、不丢上下文、成本低一个数量级。

**判据**：想借外部视角前先问一句——我要的是「多一种判断标准」，还是「多一双能跑代码的手」？
前者找专家，后者找子代理。都不是，就别接。

## 九、静默 bug 的三种样子（v0.73.3 夜审沉淀）

七个修复里最值得记住的不是修法，是它们共同的「静默」：编译过、测试绿、真机上坏。
以后新写代码，按这张表自查：

| 样子 | 机制 | 本轮实例 | 检查方法 |
| --- | --- | --- | --- |
| **PendingIntent extras 冻结** | 匹配只看 requestCode + 组件，**不看 extras** | 通知栏小睡按钮连错闹钟 | intent 带 extras 的 PendingIntent 必须带 `FLAG_UPDATE_CURRENT`；全项目还得带 `FLAG_IMMUTABLE`（Android 12+ 强制，`PendingIntentFlagTest` 扫源码守门） |
| **身份编码错位** | 注册 / 取消 / 查询三方用不同字段编码同一实例 | 跨午夜提前提醒静默失效 | 「身份」三件套（requestCode / data URI / extra）必须与取消方同一套日期；排程类代码先问「跨午夜会怎样」 |
| **写死文案与动态状态脱同步** | 状态机改了，硬编码字符串没跟上 | 午夜后「明天请假」标错日期 | 凡 Model 里有目标日期 / 状态的，文案与行为都从 Model 推导，不写死；改动后搜一遍硬编码的「今天 / 明天」 |

**排程类代码的固定自检三问**（本轮三个 bug 全栽在这里）：

1. 跨午夜会怎样？（00:30 的闹钟、23:58 响 00:02 点小睡、0:00–5:00 刷通知）
2. 用户手改数据会怎样？（配置文件是纯文本 JSON，导入路径必须夹取）
3. 同一路径的别的入口怎么做的？（升级重排三个入口都 goAsync 了，onResume 是漏的那个）

**Robolectric 两个坑**（各浪费过一轮）：

- 测试 JVM 的工作目录**不一定是项目根**（gradle 跑在模块目录下）。读项目文件一律从
  `user.dir` 向上找到含目标目录的那层，别写死相对路径。
- `PendingIntent.send()` 对 **broadcast intent 不派发**（service intent 可以）。
  验证广播接收行为直接调 `receiver.onReceive(ctx, intent)`，别绕 PendingIntent。

## 十、在系统的地盘上，不要自己画颜色（2026-10-29，通知卡片五连败的结论）

**规则：系统画的东西——通知卡、锁屏、状态栏、导航条、桌面图标、系统弹窗——底色不是你的。
任何自绘色块都必然露馅，因为它不知道周围是什么色。**

两次实例，同一个错：

| 版本 | 做法 | 结果 |
|---|---|---|
| 0.89.1 | 布局自绘紫底，铺满内容区 | 系统卡片内容区外还有一圈内边距，成了「紫方块套白框」 |
| 0.89.8 | 给文字贴一块固定深靛底 | 可读性达标，但半透明卡上像贴了张标签，三块紫并排 |

正确做法（0.89.9）：**颜色写成带 `values-night` 的资源，在布局里引用，代码不参与。**
布局是宿主进程（SystemUI）inflate 的，它按自己的配置解析资源；切深浅色时它重建视图、
重新解析。颜色因此永远是对的，而且不是「我们算对的」。

**判据一句话：问「这个颜色什么时候定下来的」。**

- 构建时定（`setTextColor` / `setBackgroundColor` / 代码里读 `uiMode` 再传值）→ 会过期；
- 渲染时定（XML 里引用 `@color/xxx`）→ 跟着宿主走。

远程渲染的场景（`RemoteViews`、桌面小组件、快捷方式）**全部是「构建时定」**，
所以这类地方一律走资源引用，一个颜色都不许在代码里赋值。

守卫：`NotifThemeTest.notifSources_neverSetTextColor` 扫五个通知类，
`NotifThemeTest.layouts_useSemanticColors` 扫两个布局。

## 十一、视觉改动先在本地渲染真像素，再出包（2026-10-29）

**规则：没有本地渲染图，不许为视觉改动出包。**

代价对比很直白：六版里五版是「改完 → 打包 → 装机 → 截图 → 再改」，每轮 20 分钟
外加用户一次安装；0.89.9 第一次改成先渲染，一次过。

```java
@RunWith(RobolectricTestRunner.class)
@Config(sdk = 34, qualifiers = "night-xxhdpi")   // 顺序不能反
@GraphicsMode(GraphicsMode.Mode.NATIVE)          // 不加这行，画出来是全透明
```

渲染出透明底 PNG 后，再按**真机实测的底色**合成（通知卡：浅 `#F8F0F0` / 深 `#281818`），
浅深两张并排看。实测值的来源就是用户的问题截图——把它量出来，别猜。

**两个坑（各浪费过一轮）**：

- qualifiers 顺序必须是 `night-xxhdpi`，写成 `xxhdpi-night` 会 `failed to parse qualifiers`
  （密度限定符排在 UI mode 之后）。
- 不写 `@GraphicsMode(NATIVE)` 时 PNG 全透明，而且「浅色」「深色」两张**字节数一模一样**——
  那就是没画上去的信号，不是「两种模式一样」。

**指标全过不等于好看。** 0.89.8 三档文字全部过 AA、735 条测试全绿，用户一眼「这也太丑了」。
对比度是下限，不是设计；本地渲染图能补上一半，最后那一半仍要用户看实物。

## 十二、用户说「和上次犯的是同一个错」，就往上退一层

**规则：连续两版没解决同一处问题，停止调参，重述问题。**

0.87.7 → 0.89.8 一共五版，每版都在「这次哪边糊了 → 换成哪个颜色」，从没有人问
「为什么字色不跟着变」。用户一眼看出 0.89.8 和 0.89.1 是同一类错（都是在系统卡上自己画），
共同点其实一直摆在那儿。

**判据**：用户第二次说「还是不对」或「和上次一样」，就不再动参数，改做三件事——

1. 用一句话重写问题（不是「哪边看不清」，而是「颜色在什么时刻定下来」）；
2. 列出所有可能的原因层级（症状 / 机制 / 前提），指出前面几版停在哪一层；
3. 挑能一次解决底层的那条，哪怕改动更大。

这比第六版再调一次颜色便宜得多。

## 十三、GitHub 推不上去：先分清是链路断了还是协议断了（2026-10-30 修订）

这一节最初写的是「HTTP/2 会被掐断，加 `-c http.version=HTTP/1.1` 就好」。**那个结论是错的。**
2026-10-29 加了参数确实一次通过，10-30 再推，`HTTP/1.1` 一样超时——两件事只是挨得近，
不是因果。这是第五节「需要解释自己的机制」的又一例，而且是我自己犯的。

### 症状

推 v0.90.3、v0.90.4 时反复失败，报错换着花样：

```
Failed to connect to github.com port 443 after 133791 ms: Couldn't connect to server
fatal: unable to access '...': GnuTLS recv error (-110): The TLS connection was non-properly terminated
fatal: could not read Username for 'https://github.com': No such device or address
```

### 三条命令分清

```bash
# 1. 别的 GitHub 入口还活着吗
curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' https://api.github.com

# 2. 推送端点
curl -s -o /dev/null -w '%{http_code}\n' \
  "https://github.com/<owner>/<repo>.git/info/refs?service=git-receive-pack"

# 3. SSH 走 443
ssh -T -o ConnectTimeout=8 -p 443 git@ssh.github.com
```

判读：

- **api 200、receive-pack 超时、ssh 秒回** → `github.com` 这个主机被间歇阻断。
  跟 HTTP 版本、凭证、仓库状态都没关系，换 `http.version`、换 IP 都不会好。
- **`could not read Username`** → 第三件事：沙箱重启后凭证助手返回空，与网络无关，
  别把它和上面混成一个故障查。
- **三条全通但 push 还失败** → 才轮到仓库侧（非快进、保护分支、令牌权限）。

2026-10-29 深夜实测：`github.com` 解析出的每个 IP 上，网页、upload-pack、receive-pack
全部超时；同一分钟 `api.github.com` 200 / 0.38s，`ssh.github.com:443` 三次全部秒回。
还抓到过更细的一层——同一个 IP 上 `git-upload-pack` 401 秒回、`git-receive-pack` 超时，
说明是**按主机名的间歇阻断**，不是端口不通。

### 三条应急通道

| 通道 | 做法 | 代价 |
|---|---|---|
| 等空窗 | 隔几分钟重试 | 0.90.0–0.90.3 都是这么上去的，不可控 |
| SSH over 443 | `ssh.github.com:443`，配 **Deploy key** | 一次性配置；但沙箱销毁私钥就没了 |
| Git Data API | 全程只碰 `api.github.com`，不经过 `github.com` | `tools/push_via_api.py`（分支 + 标签）、`tools/publish_release.py`（Release + 资产） |

SSH 那条务必用 Deploy key，别用账号级 SSH key：后者对你名下**所有**有写权限的仓库有效、
GitHub 没有给它设过期日的功能；而沙箱是临时的，私钥随沙箱消失，公钥就成了一辈子用不上
又删不掉的僵尸。Deploy key 只对这一个仓库生效，还能勾只读，泄露面小一个数量级。

### Git Data API 的硬护栏

手工拼 blob / tree / commit，只要差一个字节，算出的 SHA 就和本地不同，远端历史会和本地
分叉——这是这条路唯一真正的风险。所以 `tools/push_via_api.py` 每一步都比对：

- 每个 blob 上传后的 SHA == 本地 `git rev-parse <commit>:<path>`
- 建出的 tree SHA == 本地 `<commit>^{tree}`
- 建出的 commit SHA == 本地 commit SHA
- 任何一处不等就退出，**ref 一行不动**

10-30 首次跑就被这道闸拦下：提交消息末尾的换行被脚本里的 `.strip()` 吃掉，667 字符
变 666，commit SHA 从 `dde7292` 变成 `f73033a`。远端毫发无损，改掉后一次通过。
**没有这道闸，那就是一次历史分叉。** 手工构造对象的出错概率是实打实的。

### 标签和 Release 也在同一条通道上（v0.91.3 补）

`git push` 推不了的时候，标签和 Release 自然也推不了，但这两件事在 `api.github.com` 上
都能做，而且能和分支共用同一条链路：

| 要做的 | 命令 | 关键点 |
|---|---|---|
| 推标签 | `tools/push_via_api.py --tag v1.0.0` | annotated 走 `/git/tags` 重建，SHA 比对不过就不建 ref |
| 推全部标签 | `tools/push_via_api.py --tags` | 已存在且相同就跳过 |
| 建 Release + 传 APK | `tools/publish_release.py --mapping` | 幂等：Release 复用、同名资产跳过 |

几条经验：

- **annotated 标签能校验，lightweight 只能信任。** 前者中间有一层 tag 对象，自己带 SHA，
  可以照提交那套「先建、再比对」；后者直接指到提交，建 ref 而已，没有可比对的东西。
  所以发版统一用 `git tag -a`。
- **标签名写错比分支名写错更难收拾。** 移动一个已发布的标签会让别人的克隆静默分叉，
  所以脚本对「远端已有同名但指向不同」一律报错退出，不做 force。
- **资产名要和 `version.json` 里 `apk` 那条 URL 完全一致**，否则「检查更新」给出的下载地址
  是 404。版本号统一从 `version.json` 读，不手打。
- mapping.txt 一起传。14MB 不算小，但用户报崩溃时，没有它只能看类名和行号。

---

### 不变的三条

1. 令牌只走一次性 URL，**不写进 `.git/config`**，也不 `git config credential.helper store`。
2. 不要 `sleep` 干等、不要原样重试同一条命令。三次同样的失败已经证明不是抖动，换通道。
3. 推完用 API 核对 `commits/main` 的文件增删行数，别只看 push 命令的返回码。

## 附：这套流程解决不了什么

诚实说清楚边界：

- **真机行为验证不了**。AlarmManager 到点是否真响、厂商 ROM 会不会杀后台、状态栏给不给
  小闹钟图标，这些只有用户装机才知道。所以试用期的验证点必须问，不能跳。
  （**通知长什么样不在此列**了——真像素渲染能看个八九不离十，见第十一条。）
- **视觉审美判断不了**。渲染图能定结构和配色，定不了「好不好看」；最后仍要用户看实物。
  但**能提前挡掉明显难看的方案**，这一层以前是直接跳过的。
- **用户只有一个**。「这个功能有没有用」这类判断没有样本，只能靠推理和试。
  所以宁可先做小的、可撤的，也别一次上大的。
