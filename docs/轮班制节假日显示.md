# 轮班制的法定节假日怎么显示

> 状态：**研究中，等用户选方向**（2026-11-10 15:08 用户提出）。代码一行未动。
> 触发：用户切到轮班制后看首页日历，发现春节那几天不显示节假日颜色。

---

## 一、用户看到的，和代码实际做的

以 2027 年春节为例（假期 2/5–2/13，共 9 天）。轮班用「4 天上 2 天休」探针跑出来是这样：

| 日期 | 星期 | 判定 | 法定假 | 格子现在写 | 底色 |
| --- | --- | --- | --- | --- | --- |
| 2/5 除夕 | 五 | 上班 | 是 | **除夕** | 上班色 |
| 2/6 初一 | 六 | 上班 | 是 | **春节** | 上班色 |
| 2/7 | 日 | 休息 | 是 | 休 | 休息色 |
| 2/8 | 一 | 休息 | 是 | 休 | 休息色 |
| 2/9 | 二 | 上班 | 是 | 班 | 上班色 |
| 2/10 | 三 | 上班 | 是 | **圣灰** | 上班色 |
| 2/11 | 四 | 休息 | 是 | 休 | 休息色 |
| 2/12 | 五 | 休息 | 是 | 休 | 休息色 |
| 2/13 | 六 | 上班 | 是 | 班 | 上班色 |

两件事一眼能看出来：

1. **九天的法定假，只有两天有节日名**，而且那两个字是「农历节日」那一层给的（除夕、初一），
   不是「法定节假日」那一层——后者在轮班模式下根本没被调用。
2. **2/10 是上班日，却写着「圣灰」**。这是 `DayTag` 既有的优先级（基督教节日排在「班/休」之前），
   与轮班无关，是独立问题，见第六节。

其余七天，格子和一个普通周二没有任何区别。

## 二、根因：一个开关同时管「行为」和「显示」

`WeekSchedule.dayType` 第 419 行起：

```java
if (rule.mode.isCycle()) {
    if (rule.cycleHoliday) {                     // 默认 false（轮班）
        if (HolidayData.isMakeupWorkday(d)) return DayType.MAKEUP_WORK;
        if (HolidayData.isHoliday(d)) return DayType.HOLIDAY;
    }
    return isCycleWorkday(d, rule) ? DayType.WORK : DayType.REST;
}
```

`cycleHoliday` 的本意是**行为开关**：开着，春节那九天闹钟不响；关着，照常响。
轮班多是医院、工厂、安保，春节照上班，所以 `Prefs` 里给轮班的默认值是 `false`。
这个默认值不能动——改了会让一批人的春节闹钟集体不响。

但同一个 `false` 顺带把**显示**也关掉了：`dayType` 不返回 `HOLIDAY`，日历就永远不知道
那天是法定假。而打开它的代价是闹钟不响。

所以轮班用户面对的是二选一：

- 要日历上有节假日 → 春节闹钟不响 → 不行；
- 要闹钟照响 → 日历上什么也看不到 → 现在这样。

**这不是「少画了一个颜色」，是把两件事绑在了一个开关上。**
闹钟编辑页那句提示也印证了这一点：「春节、国庆自动标成『休』，只对这一条生效」——
用户读到的是「标成休」，而不是「那天不响」。

### 自定义为什么没这个问题

`Mode.CYCLE` 一个枚举同时装着「自定义（固定 7 天）」和「轮班（2~62 天）」，
区别只在 `Prefs.getCycleKind`：自定义默认**跟**节假日，轮班默认**不跟**。
所以同一个 bug 在自定义模式下不出现——不是因为那边写对了，而是因为那边开关是开的。

## 三、十款同类 App 怎么做（2026-11-10 联网查证）

| App | 地区 | 节假日怎么标 | 底色归谁 |
| --- | --- | --- | --- |
| 我的排班表 | 国内 | 法定假日**红框圈出来** | 班次色（早班浅蓝/中班浅黄/夜班深灰） |
| 轮班日历 | 国内 | 与班次色块**并列标注**农历与法定节假日 | 班次色 |
| 安心排班日历 | 国内 | 法定节假日**自动标红框**，可一键切成节日班或休息 | 班次色 |
| 排班管家 | 国内 | 节假日**自动高亮** | 班次色 |
| 点点排班 | 国内 | 直接标出「休」和「班」两个字 | 班次色 |
| My Roster（MeinDienstplan） | 德国 | 节假日**独立配色**，月份/年/小部件都标；`today / 节假日 / 节假日以外的假 / 请假 / 无班` 各有自己的颜色 | 班次色 |
| ProShift | 德国 | 官方节假日直接标在日历上，与「班次色 + 字母」并存 | 班次色 |
| ShiftScheduleUp | 美国 | 原文：holiday days are **tinted** so you can see **which of your shifts land on a public holiday**，理由写着「影响 holiday pay 和调休」 | 班次色 |
| ShiftPay | 英国 | 「Show public holidays for your work region」，与 rota 并列 | 班次色 |
| ShiftCycle | 美国 | 内置节假日，且节假日是**加班费加成**的一个参数 | 班次色 |

**十款全部显示节假日，没有一款用节假日替换「上班/休息」。**
底色一律留给「今天上什么班」，节假日是叠加上去的第二层。

原因写得很直白（ShiftScheduleUp 的产品文案）：对轮班的人，节假日不是「放假」，
是**「我这班落在节假日上」——关系到三倍工资和调休**。
信息主体是「上班」，节假日是那天的属性，不是那天的替代品。

这一条推翻了我们之前四个方案的共同前提。数字色 / 描边 / 黄底 / 圆点，
四个都在争「底色或字色归谁」——而正确答案是**底色从一开始就不该归节假日**。

## 四、三个问题的回答

### 1. 轮班制有没有必要显示节假日

**有，但语义要改。**

- 双休用户看到「假」= 那天不用上班；
- 轮班用户看到节假日 = 那天照上班，但**值三倍工资 / 可以调休 / 家人放假**。

后者的信息量不比前者小。医院、工厂、安保的人月底算加班费，第一件事就是数「这个月有几个班落在法定假上」。
现在这个 App 给不出这个数，日历上也看不出来。

### 2. 图例要不要跟着变

**要，而且现在的图例在轮班模式下是假的。**

图例六项（上班 / 休息 / 节假日 / 调休补班 / 请假 / 加班）里，
「节假日」那一项在轮班模式下**永远不可能出现**——因为 `dayType` 不返回 `HOLIDAY`。
图例在教用户认一个日历上不存在的颜色。

这也是判断方案好坏的一把尺子：**如果一个方案要求图例随模式变，那它就是错的**——
同一个 App 长两套图例，等于承认这套语言不自洽。

### 3. 大小周 / 自定义要不要一起考虑

**要，但分界线不是「哪个模式」。**

真正的分界是：**这张排班表由「星期 / 法定日历」决定，还是由「周期」决定？**

| 模式 | 排班由谁决定 | 节假日能不能改变「上不上班」 |
| --- | --- | --- |
| 双休 / 单休 / 大小周 | 星期 | 能——国家说放假，那天就不上 |
| 自定义（7 天） | 星期（勾周几） | 能，同上 |
| 轮班（2~62 天） | 周期计数 | 不能——上 N 休 M 与日历无关 |

前三种模式下，「节假日」和「不上班」是同一件事，底色画成「假」是对的（现在的做法没错）。
只有轮班这一种，「节假日」和「上班」会同时成立。

所以这不是「轮班要不要特殊照顾」，而是**轮班模式多了一种别的模式不会出现的组合状态**：
上班 + 法定假。现在这一格没有地方放第二个信息。

## 五、两个方向

### 方向 1：只补轮班，双休那边不动

轮班模式下，法定假日那天加一层标记（框 / 底线 / 角标），底色和「班/休」照旧。
图例在轮班模式下多一项，或把「节假日」那项改成框的样子。

- 改动小，只碰 `dayType` 的一个分支 + 日历渲染 + 图例；
- **代价**：图例随模式变，同一个 App 两套图例。用户问的第二个问题，答案会变成「是，要变」——
  这本身就是个坏味道。

### 方向 2：把「底色」和「节假日」彻底拆开（推荐）

**底色只回答一件事：这天要不要上班**（上班 / 休息 / 请假 / 加班 / 补班）。
**法定节假日改成叠加层**（框），所有模式统一。

| 场景 | 现在 | 方向 2 |
| --- | --- | --- |
| 双休 · 10/3 国庆 | 黄底「休」 | 灰底「休」+ 框 |
| 轮班 · 2/6 春节且上班 | 蓝底「班」，无任何标记 | 蓝底「班」+ 框 |
| 轮班 · 2/7 春节且休息 | 灰底「休」，无任何标记 | 灰底「休」+ 框 |
| 补班日 | 「补」色 | 不变（补班本来就是行为，不是性质） |

- 一套语言，一个图例，所有模式同一套规则；
- 图的语义干净了：**底色问「上不上班」，框问「是不是法定假」**；
- **代价**：双休用户习惯了「国庆整片黄」，改成灰底 + 框会觉得弱了。
  这是真实的视觉降级，不是我在替谁权衡——需要用户看过图再定。

### 不推荐：不改

用户明确说「这个事情没有想象中的那么简单」，说明要的不是「算了」。
而且这一格确实缺一个信息，不是审美问题。

## 六、顺带发现的独立问题：「圣灰」盖掉班/休

2027-02-10 是上班日，格子上写的是「圣灰」（基督教圣灰星期三），底色是上班色。
`DayTag` 的优先级是「法定假名 > 农历节日 > 节气 > 基督教节日 > 班/休」，
基督教节日排在「班/休」之前，所以任何一天只要碰上圣灰、复活节，就看不到「班/休」两个字。

这条和轮班无关，双休用户也会遇到（只要开了「基督教节日」开关）。
但它和本次是同一类病：**辅助信息顶掉了主信息**。

建议单独处理：基督教节日、节气这类「今天是什么日子」的信息，不该抢「上不上班」的位置。
是否要改，等方向定了一起说——如果方向 2 落地，「框」会接管「节假日」这件事，
`DayTag` 的优先级可以顺势收一收。
