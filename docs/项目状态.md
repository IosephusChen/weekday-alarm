## 2. 开工第一步（别跳过）

```bash

```

期望 **864 个用例，0 失败**。这一条同时验证：JDK 通了、SDK 通了、依赖拉全了、代码完整。
数字对不上先查环境，**别急着改代码**——在坏地基上改出来的东西没法判断对错。

**环境只在一处写**：JDK 17+、SDK `android-34` + build-tools `34.0.0`、SDK 缺失时的补装命令、
`~/.gradle/init.gradle` 的语法坑与正确写法、签名指纹——全在 `恢复说明.md` 第 1 节
（环境是第 2 步、密钥是第 3 步）。这里不重复。只记一条：**首次构建要拉约 700MB 依赖，5–15 分钟，用 `run_in_background` 等**。

签名对不上 = 打出的包装不上（手机报「签名不一致」，只能卸载重装、设置全丢），所以密钥必须先放回
`~/.android/debug.keystore`，再动构建。

### 发版清单（每版走一遍）

1. `app/build.gradle`：versionCode +1、versionName 按规则改
2. `Changelog.java` 顶部加 `Entry`，**code 必须等于 versionCode**（`ChangelogTest` 校验，对不上测试红）
3. 同步 `打工人闹钟-使用说明.md`（**头部版本号最容易漏**）与 `更新日志.md`
4. 跑 `tools/release.sh --check`：它一次性校验五处文档 + 全量测试 + lint，
   哪处没跟上会直接点名（不用等 Gradle 跑完 40 秒才发现）
5. `tools/release.sh` 出包：复制到构建输出目录、算 MD5 与字节数、提示回填位置
6. 回填交接文档现状表的 MD5，更新 `布局现状清单.md`（若动了布局）
7. `git commit`
8. **推 main**：`git push origin main`。沙箱里 `github.com` 直连常被掐，走
   `tools/push_via_api.py --branch main`（逐提交比对 SHA，最后才动 ref）。
   **恢复包 clone 出来的 `origin` 指本地 bundle，要先改指 GitHub**（一条命令，见
   `docs/恢复说明.md` 第 1 节），否则脚本第一步就报「看不懂 remote 地址」
9. **打 tag 并推**：`git tag -a vX.Y.Z -m "<标题 + 要点>"`，
   再 `tools/push_via_api.py --tag vX.Y.Z`。**逐个传 `--tag`，别用 `--tags`**——
   本地有个历史标签 `archive/v1.47.0-dropped` 指向不在远端的提交，`--tags` 会撞在它上面停下
10. **建 Release**：`tools/publish_release.py --mapping`（幂等，正文取 `version.json`
    的 title 与 notes，资产自动命名成 `weekday-alarm-X.Y.Z.apk` + `mapping-X.Y.Z.txt`）。
    先 `--dry-run` 看一眼，**别临时写脚本**——1.0.10 那次就是临时写了一个，
    做完才发现项目里本来就有这个工具。发完验三件事：
    `releases/latest` 是这一版、资产 SHA-256 与本地一致（`sha256sum` 对 API 的 `digest`）、
    raw 的 `version.json` 是新版本。
    **jsDelivr 那条不必再等**：v1.2.0 实测 purge 对 `@main` 已无效（见文首），
    `@vX.Y.Z` 反倒是新的；App 从 252 起两源取高，不再依赖 CDN 及时。

> **一次补发多版**：走 `tools/publish_pending.py`（2026-11-03 加）。它**不重复**
> `publish_release.py` 的逻辑——只是按 `Changelog.java` 的顺序逐版生成临时
> `version.json` 再调它，外加两道闸：开跑前把整批 APK 与 tag 都校验一遍，
> 以及 `--from-code` 卡死范围（GitHub 建 Release 时 tag 不存在会**从默认分支造一个**，
> 比不发还糟）。十版手改十次 `version.json`，漏一次就是两个版本之间断档。
> tag 仍然逐个推，循环写：
> `for t in v1.8.0 v1.8.1 …; do tools/push_via_api.py --tag $t || break; done`

> **为什么有脚本**：一次发版要动五处文档、跑两轮 Gradle、复制 APK、算 MD5，
> 全靠人记就会漏。脚本把「能自动判的」全判了，只剩「需要写字」的留给人。
>
> **但 `release.sh` 只管本地产出，远端一步都不走**——1.0.2 ~ 1.0.9 就是这么攒下八个
> 没发布的版本的（见第 8 节）。**「出包」和「发布」是两件事**，第 8 ~ 10 步不做，
> README 上的下载链接就是 404。

**哪些改动必须上真机**（2026-10-28 定，用户手上只有一台小米）：

## 3. 阶段前提：现在是发布前，正确性优先

**所以现在**：任何「为了不丢老用户设置而妥协」的做法都是错的，该改就改。

## 4. 版本号规则（2026-10-26 重定：0.x 测试期 → 1.0.0 上线）

用户 2026-10-26 拍板：**测试期从 v0.x 起排，v1.0.0 留给正式上线那一天**。
理由是 v1.x 这个号段一旦用掉就回不去了，而测试期还会有删功能、改备份格式这类
破坏性改动——0.x 本来就允许这些（semver 惯例），1.0.0 才该是「承诺稳定」的时刻。

| 改动性质 | versionName |
| --- | --- |
| 加功能 / 改交互 / 删局部功能 / 界面重做 | **次版本 +1**，修订归零（0.80.0 → 0.81.0） |
| 修 bug / 调文案 / 调布局 / 纯文档 / 构建项 | **修订 +1**（0.80.1） |
| 正式上线 | **1.0.0**（之后按上两行继续） |

**判定口径**（有歧义时照这个判）：

- **改交互**：用户的点法变了——开关换成整行进对话框、弹窗从「按确定」改成「点即生效」。
- **调布局**：点法没变，只是位置、大小、颜色、字重、文案变了。
- **删局部功能**：删掉某个入口或某块 UI，主流程还在（删小组件上的请假按钮就属这档）。
- 只有「删掉一个主要能力」（比如整个请假体系、整个小组件）才够主版本——测试期不设主版本。

**versionCode 铁律**：每打一个包 +1，**永不复用、永不回退**。跳号允许且正确，空号不回收
（v0.56.0 撤掉年度闹钟那次跳过一个号，重排后跳号被抹平了，但规则不变）。

**versionName 与 versionCode 一一对应**：2026-10-26 重排后两条序列严格同步——
name `0.1.0 → 0.80.1`、code `1 → 182`，同一件事的两个写法。

   时刻——新模型下连固定时刻都没有。**「要加班」要变成「加哪个班」**，单日覆盖存班次 id。
2. **两个真相源。** 请假、加班各存一个日期集合，而「这天是哪个班」是同一个信息。
   不合并会出现「标了加班但那天是休息」。**单日覆盖统一存 `date → shiftId`**，请假 = `-1`。
3. **`DayType` 不要塞班次。** 它只答「上不上班」，班次单独查。一塞进枚举，上面 7 个
   显示文件全要改签名，等于自己制造工程量。

> **2026-11-04 收口**：`Prefs.KEY_DAY_PLAN` 存 `date → shiftId`（`-1` 请假、`-2` 老数据的
> 「加班没说哪个班」），`Rule.days` 跟着它走，`dayType` / `shiftOn` / `isScheduledWorkday`
> 都是「先查表，表里没有按规则算」；请假成了 `DayType.LEAVE`，`DayType` 里**没有**塞班次
> （洞 3 的约定守住了）。`Alarm.timeOn` 在**所有**模式下都认覆盖层里的班次——原来只在
> 「N 天一轮」里认，双休用户选了夜班也照样按早上响，这才是「8h / 12h 下班点不齐」的根。
> 老的两个日期集合只在迁移时读一次，键保留以便回滚。细节见 `更新日志.md` 的 v1.11.0。

  3 次点击变 1 次）。将来若要动，走这条，别再去挪行。
- **轮班走「班次」模型，别再退回一张表（2026-11-03 拍板）**。用户原话：「肯定是『明天我上夜班』
  比『18:30、00:30、次日 8 点各响一次』简单，后面那个实在太复杂了。」前面十轮争的「第 N 段 /

  边界：双休 / 单休 / 大小周没有班次，一行不动。
- **这个 App 是「按排班决定几点响的闹钟」，不是考勤工具（2026-11-04 拍板）**。起因是
  「假加」随 v1.11.0 被合并成「请假」——用户问「在 App 里体现考勤信息是否必要」，
  结论是**不必要**。所有标记只回答一个问题：「那天几点起」。请假 = 不响，班次 = 按这个
  点响，都是**对未来的指令**，不是对过去的档案。「白天请假、晚上加班」标成夜班即可——
  请假这件事对「今晚几点起」没有输入价值。

  「这月请了几天」「加了几次班」，然后把闹钟拖成半个考勤 App，而它永远对不上公司的账，
  还会拖累「明天几点起」这一个可信指标。真需要考勤的信号是「想把记录导出成表」，

  **和 v0.51.0 那次不矛盾**：那一轮砍的是「工时统计 / 半天粒度 / 独立 app」，只留下「双标记」
  当作「心里有个数」的最小实现（见 `优化与新功能建议.md` 四之四）；这次拿掉的正是那个最小值。
  两轮的尺子是同一把：**记录类的东西能做多小做多小，一旦妨碍排程就让位。**
  **术语也跟着定死（v1.11.1，v1.11.2 补边界）**：「加班」只用在休息日；上班日的同类操作
  在轮班里叫**调班**——换成别的班，影响的是那天几点响。双休 / 单休 / 大小周没有「班」这一维，
  上班日只有「请假」，别再把调班入口塞回去。判断统一走 `Rule.hasShifts()`
  （v1.11.3 收窄：**模式是 CYCLE 且真有一张轮班表**；只勾星期的「自定义」也算没有班），
  不看班次表里有没有残留定义——切模式时定义不删，那只是残影。
